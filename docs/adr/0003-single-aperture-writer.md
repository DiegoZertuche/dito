# Single aperture writer

Exactly one rep-side component holds Ledger write credentials, accepting two input classes. **Class 1 — candidate facts**: model output, untrusted, confidence-gated; below-threshold candidates become questions, never facts (amended 2026-09-09: they are dropped, never facts, never questions). **Class 2 — rep acts** (confirmations, corrections, retractions, entity create/rename/merge): each must reference verifiable rep-act evidence — a dashboard interaction id or the WA message id of a rep-authored, raw plane-delivered message — matched by deterministic code, never by model output; anything not evidence-bound is processed as class 1. Entity rows are Ledger data: they mutate only through the aperture, and every entity mutation appears in the daily disclosure. The aperture files a fact and enqueues its disclosure line **in one Postgres transaction** (FR-72). It owns the question and disclosure lifecycle: disclosure lines (already-crossed content) live plaintext in a seat-scoped rep-side store; **questions (uncrossed rep content) live aperture-side as twin-DEK ciphertext**, decrypted only at delivery — so disclosure never depends on lease availability. Aperture infrastructure is seat-scoped: it outlives twin sessions and serves the closing window.

Chosen because Ledger write-credential sprawl and model-laundered "rep corrections" are the two failure modes that would quietly break the crossing discipline.

**Amendment 2026-08-29 (which entity mutations are disclosed).** "Every entity mutation appears in the daily disclosure" is narrowed to a principle: **an entity mutation is disclosed when it carries rep-derived content across the wall, not when it restructures what already crossed.** Entity **create** and **rename** are disclosed — both put a name taken from the rep's conversation into the Ledger for the first time, and a name is the entity field most likely to carry something personal, which is exactly what the receipt and its correction window (ADR-0026) exist to catch. **Merge is not disclosed**: it files no fact, moves nothing across, and rearranges company data that already crossed and already had its window. The disclosure is the crossing receipt, and its completeness claim (FR-38) is about what crossed — narrowing the rule to that is what keeps the claim true rather than curated. Merge is also no longer a rep act at all (ADR-0035), so there is no rep-authored evidence to bind: a machine-performed merge is stamped as such on the edge. Class 2 otherwise stands unchanged for create and rename.

**Amendment 2026-08-29 (what "never by model output" binds).** The determinism requirement above binds the **evidence and the target**, not the **intent**. Evidence — the WA message id of a rep-authored, raw plane-delivered message, or a dashboard interaction id — and the target it names — the quoted twin post, and the line within it, resolved by deterministic join — are never model-produced, exactly as before. What may now be model-read is the *intent*: whether a given rep message is a decline, a correction, or an answer. This is permitted **only for acts whose effect is reversible inside the disclosure window** (ADR-0004's provisional 24h). The two acts that are not — a **customer send** and a **chat↔entity binding** — keep a deterministic verb match on top of the deterministic evidence, per [ADR-0037](0037-the-twin-talks-like-a-coworker.md). The named failure mode is still fenced: a model cannot manufacture a rep act out of nothing, because it supplies no evidence, names no target, and cannot mint a tap (ADR-0006's two non-model minters stand unchanged). What it may do is read a real rep message, about a real post, and be wrong about it — which costs the rep one sentence to say again, and is the trade [ADR-0036](0036-no-architecture-tax-on-reps-or-owners.md) already accepted.

**Amendment 2026-09-05 (the line within the quoted post, when the rep names no number).** The amendment above lists «the line within it, resolved by deterministic join» among the things never model-produced, and slice 5a's build ([#174](https://github.com/Dito-Core/dito/issues/174), ruled at [#177](https://github.com/Dito-Core/dito/issues/177)) found the join has nothing to resolve when the rep's words carry no printed number — spec #171's own example is «no fueron 50, fueron 15». Stated precisely: **where the rep's message names exactly one number the quoted disclosure printed, code resolves the line and a tool call naming a different one is refused; where it names none or several, the model's reading of which line the rep meant stands.** What bounds the second case is the same fence as before — the model can only pick a line the rep was shown, the evidence and the quoted post are still deterministic, the fact is annotated rather than deleted inside the correction window, and the receipt names the line back so a misread costs one sentence. Refusing that case would refuse the sentence the spec says the rep may speak. Whether the reading should ever be stricter is recorded on the horizon ([#117](https://github.com/Dito-Core/dito/issues/117)).

**Amendment 2026-09-09 (class 1 below the gate drops; class-2 evidence has two surfaces).** Two corrections from slice 6a (spec [#214](https://github.com/Dito-Core/dito/issues/214); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))). First, the class-1 sentence above — *below-threshold candidates become questions, never facts* — now reads **below-threshold candidates are dropped, never facts, never questions**: [ADR-0043](0043-a-question-is-a-service-never-a-plea.md) rules that the twin never asks the rep to fill a hole in the record, and a confidence number is a hole in ours. The drop is counted on the run record; the candidate-question machinery that carried the old route was retired with it ([#220](https://github.com/Dito-Core/dito/issues/220)). Second, the class-2 evidence — *a dashboard interaction id or the WA message id of a rep-authored, raw plane-delivered message* — has both of its surfaces now: the dashboard's is a **`dashboard_acts`** row, written by rep-web's own role as the act is performed ([#224](https://github.com/Dito-Core/dito/issues/224)), and the three aperture stores that record a rep act name either surface's evidence. What the row carries is the act, its target and the session that pressed it; the aperture verifies it as it verifies a message id, by deterministic code against the seam. Nothing about intent-reading (the 2026-08-29 amendment) moves: a button is not read, it is pressed.
