# The rep notepad is twin-side only

The **rep notepad** — the rep-scoped block holding *how this rep works* (register, tú/usted default, sign-off, typical length, and their standing instructions), as distinct from the rest of twin memory, which holds facts about clientes — is twin-side state and **never crosses the wall**. It lives in the per-twin encrypted bundle and dies with the key at erasure (ADR-0009). No owner surface, view, export, or aggregate may contain it or anything derived from it, and it is never a telemetry dimension (ADR-0025) — an aggregate leaks the trait without moving a byte. There is no rep opt-in to share it: an optional share inside an employment relationship becomes an expectation, and consent under that asymmetry is not consent. "Never crosses" means never crosses **the wall** — the notepad does travel to the model provider inside the prompt, ZDR-routed under ADR-0015.

**Provenance decides what crosses, not content.** A rep-stated item never crosses even when it names an entity, while the same sentence extracted from a customer conversation is a candidate fact and crosses through the aperture as normal: *"con Fuentes siempre de usted"* typed by the rep stays twin-side; *Fuentes prefers formal register*, inferred from the conversation with Fuentes, does not. The test is who said it and to whom — mechanically, whether the message's chat is the twin thread — never whether the sentence reads as being about the rep. This binds now rather than later, because the twin thread is already an ingest surface: without the rule, the batch extraction introduced with the Ledger crossing would read the rep's own instructions and disclose them to the owner as candidate facts.

**The notepad shares the twin's lifecycle exactly.** It does not migrate to a re-issued seat, and there is no rep-facing export. A rep whose seat is retired starts blank and re-teaches — affordable precisely because the notepad is hard-capped (shape and size settled at the schema session), and a better trade than notepad content outliving the key that was meant to destroy it. Export is refused for the same reason the opt-in is: a downloadable file is a thing an owner can ask a rep to produce, which reopens the rule from the other side. The rep reads, edits, and deletes the notepad on the dashboard, the only surface that carries anything but the twin (ADR-0031); the twin thread acknowledges a write in a compact line but reviews nothing, and there is never a digest of what the twin has learned.

**Storage (schema session, 2026-08-29).** The notepad is its own table in the bundle at the next free bundle schema version when it is built (ADR-0029 assigns numbers by build order; an ADR never reserves one — v5 went to reactions, ADR-0041) — one text column, not a row per rule, because a cap only forces a merge if the unit of overflow is prose that can be consolidated; capping rows would only ever *drop* one. The cap is **1,500 characters**, checked with `length()` at the write: characters rather than tokens so enforcement needs no tokenizer and does not drift when the ADR-0015 model ladder changes, and 1,500 rather than more so the cap actually binds — a standing rule runs about thirty characters, so a larger budget would hold dozens and the forced consolidation would never fire. Writes are **append-only versions with the latest row current**, because consolidate-and-retry rewrites the whole block and a rewrite can silently drop a rule; one extra column buys recoverability against the one failure mode the cap itself creates. FR-73's bundle-resident store count moves from seven to eight.

Chosen so the wall's promise holds for the rep as well as for their clientes. The notepad is exactly the material an owner would most want to see and would most damage trust by seeing — *"gets terse under pressure"* is useful to the twin and a catastrophe on a dashboard — and the Ledger crossing, whose whole thesis is what crosses, is the moment someone reasons their way into putting it there.

**Amendment 2026-09-26 (built: a save writes across two stores).** Mi libreta is built as drawn ([#264](https://github.com/Dito-Core/dito/issues/264), PR [#283](https://github.com/Dito-Core/dito/pull/283)). A save is the dashboard act `edit_notepad` — a `dashboard_acts` row that names **no target**, since a twin has one notebook and the seat on the row already says whose — and its version is appended to the bundle with that row's id as its evidence, read back through the rep-evidenced gate before the write, as every card's act is. The act row and the version live in different stores, Postgres and the bundle, and share no transaction, so the order is fixed rather than left to chance. **The act row commits first**, as the evidence, so no version ever stands without the row it names. **The version is then appended under the act row's `FOR UPDATE` lock, inside the transaction that commits the act's account** — the outcome stamp, the execution record and its chain entry, [ADR-0020](0020-hash-chained-audit-log.md)'s pair — so the write and its account are decided by one holder of the row. And **the lease holder's pass settles any act whose account never landed** — a crash or a lost connection between the two commits — from what the bundle holds, a minute after the press: `performed` under the execution id the version already carries, `refused` when the bundle holds no version for that act, taking the same lock first. Whichever writer comes second finds the row stamped and writes nothing, so the account lands exactly once and never says the opposite of the bundle. Three more things the build made precise. A save **names the version it was based on** and is refused `stale` when the thread wrote in between, exactly as `write_notepad` is refused, so a rule taught on the phone is never dropped by a save on the laptop. A text past the cap is refused **before any row is written**, with the store's two numbers and never a second copy of the rep's words. And a save that goes unanswered is not reported as «nothing changed»: the page reads the notebook first and says what it found — the version it was based on still standing, its own text now current, the thread's words, or a twin that is not answering, with the rep's text kept in the field in every case. The cap, the append-only versions and the absence of a receipt stand as written.
