# Runtime harness: Anthropic SDK Tool Runner; in-process MCP clients both sides

The agent loop is the official Anthropic TS SDK Tool Runner running inside the owning process — no third-party agent framework, no Managed Agents, no Claude Agent SDK. Each app runs its own in-process MCP client; rep integration credentials live in the bundle, owner credentials in owner-side storage; neither leaves its app. The API's server-side MCP connector is prohibited; Anthropic's server-side web tools are permitted — queries ride the ADR-0015 ZDR flow, not credentials. The owner twin uses the same harness with the owner tool surface (full FR-44 parity).

Chosen so twin memory and integration credentials never transit third-party or Anthropic-hosted runtimes, and no framework layer exists that nobody can audit.

**Amendment 2026-08-29 (one runtime; a trigger creates an execution).** There are no bespoke per-purpose harnesses. **Every unit of agentic work is an execution**: something happens, a trigger fires, and that creates a workflow — an agent execution with its own instructions, its own tool list, and its own context. Sessions are separate per execution; an execution handling an inbound customer message is not the session that talks to the rep. The agent inside decides what to do, **including deciding to do nothing** — the "does this even need a reply?" judgment moves inside the execution rather than being made by code that then calls a narrow model. This replaces the fixed harness-per-purpose shape (drafting, self-chat Q&A, extraction, and the owner twin's fourth) with one runtime invoked many ways, and makes rep-defined automations one more trigger rather than a separate mechanism.

**Amendment 2026-09-03 (a refused submission is feedback; `failed` means never accepted).** An execution submits its answer through one typed contract, and the runtime records exactly one accepted submission — a second call after an accepted one is refused, so nothing can silently replace what was recorded. A submission the contract *refuses* is not that: it recorded nothing, and the refusal goes back to the model as the tool's answer, the one place the model learns the rule it broke, so it may submit again inside the budget it already has. A turn whose every attempt is refused ends `failed`, with the last refusal named in the failure; nothing refused ever renders. This replaces the shipped "one submission, one chance", which the slice-4 boundary (Dito-Core/dito#133) showed made every live owner question fail: Sonnet 5's first answer typed the customer's name, [ADR-0037](0037-the-twin-talks-like-a-coworker.md)'s guard refused it as it should, the model resubmitted with the name as a reference — the correct turn — and the resubmission was refused as a second call. Spec #126 decision 18's "refused → `failed`" reads accordingly: refused → the model may recover; `failed` when it never does.

[ADR-0016](0016-drafting-realtime-extraction-batch-shadow-in-views.md) is unaffected: an execution carries its own budget, so extraction stays a Batch-API execution off the latency path and drafting stays inside NFR-2 — same runtime, different runs. Tool exposure is governed by [ADR-0013](0013-closed-effect-taxonomy.md)'s amendment (the gate lives on the tool, not on the execution's tool list), and what an execution may *say* by [ADR-0037](0037-the-twin-talks-like-a-coworker.md).

**Amendment 2026-09-04 (definitions are declarative specs; an automation is a wake plus a definition).** The 2026-08-29 amendment above made every unit of agentic work an execution and said nothing about what a definition *is*. Slice 4 then built the owner twin's definition as code and its trigger as a closed type with one member, while [ADR-0012](0012-one-async-machine-per-app.md) has said since triage that *"primitive definitions are declarative, serializable specs carrying a schema version"* — and nothing built so far honoured it. From slice 5a ([#113](https://github.com/Dito-Core/dito/issues/113), spec [#171](https://github.com/Dito-Core/dito/issues/171)) it does. A **definition** is a declarative, serializable, versioned spec — instruction parts, tool *names*, context-recipe *names* with the shape of their occasion-bound parameters, a submission *kind*, a budget — digest-stamped and resolved against three registries of Dito-authored parts: tools, each registered with its gate; context recipes; submissions. A definition that names a part no registry holds cannot be constructed. An **automation** is a wake plus a definition plus the parameters the occasion binds, and there are two typed wakes: a **Trigger** — an event fires it, through a predicate over metadata only; mechanisms `seam_event` and `request` — and a **Schedule** — a cadence, an enumerator over what it fires for, a precondition. The trigger record carries both its mechanism and its occasion, so the execution record and the audit entry say what a run was about and how it came to be.

**Every automation, Dito-shipped or rep-created, is an instance of that one shape.** Dito ships five besides the owner question: drafting and the twin thread (triggers on seam events), extraction and the daily disclosure (schedules, fired by the daily pass until the engine exists), and the entity-kind classification (a request from code). The safety line for the rep-created ones is the reason the gate lives on the tool ([ADR-0013](0013-closed-effect-taxonomy.md)): a rep may write instructions, pick tools and recipes by name, set a cadence or a predicate — and can never author a tool, change a gate or widen a projection, so an execution a twin assembled is safe without anyone reviewing it. **Decided, not built**: the engine that reads Schedule specs off a store and fires them durably — pause, cancel, the seat-state gate on every wake, pg-boss, which is ADR-0012's machine and belongs with the *Rep-defined automations* chunk — and the storage of a rep-created automation, which is its content in the bundle and an opaque coordination row in Postgres carrying only the metadata predicate, hard-deleted with the automation. Two things every automation takes from the runtime rather than rediscovering: a code-rendered «now» as a standard context recipe (today in the seat's zone; on the owner side also the day the FR-69 window closes), and a budget that holds the output cap — 16,000 by default — and the effort knob beside the model.

Why this and not five hand-written definitions: they cost the same to write, and only one of the two lets the sixth be written by a twin.

**Amendment 2026-09-05 (what `failed` means; `acted` is the runtime's word).** Two sentences the slice-5a build sharpened, ruled at its boundary ([#177](https://github.com/Dito-Core/dito/issues/177)). First, the 2026-09-03 amendment's heading — «`failed` means never accepted» — was too narrow: **`failed` means no submission became the execution's outcome.** A turn whose every attempt is refused is one case; a second submission after an accepted one is the other, and it stays a failure rather than a silent replacement — a model that submits twice has not finished deciding, and neither answer renders (ruled on PR #181). A response the model cut short — the budget hit before any submission — is a third, and the runtime reads the stop reason for every automation rather than leaving each to guard it. Second, **`acted` is assigned by the runtime, never by the model**: an effect tool returns a structured outcome — performed, with what a receipt is rendered from, or refused, with the reason — and the runtime records one per call and promotes the disposition to `acted` over a performed one. It promotes over a *silent* submission too. Spec #171 decision 11 said «silence is `no-action`»; read it as *silence that performed nothing*. A rep who writes «así no» quoting a draft asked for an act, not a conversation, and the twin's record must not say «the agent decided to do nothing» while the rep holds the «Descartado» receipt. `no-action` is a turn that posted nothing and performed nothing — a note to self, which calls nothing.

**Amendment 2026-09-06 (the disposition reads the filing; a Schedule takes two mechanisms).** Two corrections from slice 5b ([#179](https://github.com/Dito-Core/dito/issues/179), spec [#193](https://github.com/Dito-Core/dito/issues/193)). First, ruled on [#194](https://github.com/Dito-Core/dito/issues/194): the runtime's word for how an execution ended was read off the **submission** alone, so extraction recorded `filed` whatever the aperture did with the candidates — a day whose every candidate was refused still said `filed`. Now `runExecution` takes an optional **submission handler**, run inside the execution's transaction after the failure ladder has decided that a submission really is the outcome and *before* the disposition is fixed and the chain entry appended; the app's `dispositionOf` reads the submission **and what the handler reported**, so a disposition can be a statement about the store — `filed` means at least one candidate filed or became a question, `nothing-to-file` that none did, `posted` that the post and its question posts committed ([#196](https://github.com/Dito-Core/dito/issues/196), [#198](https://github.com/Dito-Core/dito/issues/198)). A handler that throws lands the execution `failed` with the spend the call really cost; an automation with no handler is untouched, which is why the owner twin's digest never moved. This is the 2026-09-05 sentence — *the runtime's word, not the model's* — carried one step further: not the model's, and not the model's submission either. Second, the 2026-09-04 amendment listed `request` under Trigger only. A **Schedule accepts two mechanisms** — the clock, and an operator asking the running runtime for the same occasion through the request channel ([#197](https://github.com/Dito-Core/dito/issues/197), and the disclosure's own Schedule the same way at [#198](https://github.com/Dito-Core/dito/issues/198)): one definition, one digest, and the trigger record saying which of the two asked. The channel is a content-free seam row the runtime may read and settle and never insert; the seat-state gate and the engine stay decided-not-built.

**Amendment 2026-09-09 (a seventh occasion; an execution with no model; a failed realtime execution).** Three facts from slice 6a ([#223](https://github.com/Dito-Core/dito/issues/223), [#224](https://github.com/Dito-Core/dito/issues/224); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))). **`dashboard_act` is a seventh occasion**, its mechanism `dashboard`, raised when a rep presses a button on the dashboard: the act row is the trigger's reference, and the execution it creates records what was done — a tap, a dismissal, a retraction, a binding answer, a scope switch — under the rep chain. **An execution may contain no model at all**: the scope switch runs zero iterations with no tool list and is an execution nonetheless, because the record and the chain entry are what an execution is for, and a rep act that left neither would be the one kind of work this ADR was written to forbid. And the failure ladder gains a rung for the realtime lane, ruled at the boundary and built as [#240](https://github.com/Dito-Core/dito/issues/240): **an execution that fails on what it was handed is recorded with a terminal failure disposition and its trigger's rows are marked consumed**, so the poison row is not retried on every pass; the process does not stop — [ADR-0010](0010-single-writer-lease.md) as amended says why. The one occasion that is **not** raised: an opaque delivery in the self-chat ([ADR-0042](0042-opaque-deliveries-are-seam-rows.md) as amended) wakes nothing.

**Amendment 2026-09-25 (an eighth occasion: `arrival`).** Spec [#258](https://github.com/Dito-Core/dito/issues/258) as revised, decision 15 — Diego's call of 2026-09-25. **`arrival`** is an occasion under the `dashboard` mechanism, raised when the rep opens Inicio: the local API records the arrival and the runtime wakes one execution on the realtime lane. Its submission is a **composed line** — the day's welcome on the first visit of the seat-local day, the return line naming what changed on a later one — **plus a typed curation** of the canvas, and it lands as a post of its own kind delivered to the door only ([ADR-0044](0044-the-post-primitive.md) as amended). A return within ten minutes of the last arrival raises nothing, and the last line stands. It is the first occasion whose trigger is the rep merely looking, and it stays metadata-only as every trigger must: the seat, the instant, the last arrival's instant — never content. The page never waits on it: a plain line built from typed facts renders while the execution streams and stays if it fails.

**Amendment 2026-09-27 (the harness is the Claude Agent SDK; the twin thread is one session per day).** The first sentence above — *no Claude Agent SDK* — is reversed, by the agent architecture document Diego approved section by section on 2026-09-27 ([#293](https://github.com/Dito-Core/dito/issues/293)) and the spike that measured it ([#290](https://github.com/Dito-Core/dito/issues/290)). The exclusion was written against runtimes that would carry twin memory through a third party. The Agent SDK carries nothing anywhere: it is a library that spawns a Claude Code process inside Dito's own unit ([ADR-0001](0001-three-planes-twin-is-a-logical-entity.md) as amended), and with `DISABLE_TELEMETRY=1` and `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` in that process's environment the only host it reaches is `api.anthropic.com`, measured on the spike (without them it also reaches Datadog; a remote settings and policy fetch happens at every process start regardless). What it buys is the experience the rep gets: native multi-turn history on disk with `resume` and `forkSession`, queueing of messages that arrive while a turn runs, streaming with partial messages, hooks before and after every tool call, and the file tools — and Diego's rule for the choice was the best agent experience for the rep, with cost not the deciding factor. What it costs is the process's own attachments — its environment, model identity, date and token reminders injected around our prompt — which the harness accepts.

**How it is held to this ADR's rules.** The permission model is off (`permissionMode: 'bypassPermissions'`) because the gates are ours ([ADR-0013](0013-closed-effect-taxonomy.md) as amended). The system prompt is ours, built from the definition's instruction parts and context recipes. Our tools are served as one in-process MCP server (`createSdkMcpServer({ alwaysLoad: true })`), each keeping the gate it is registered with; a `PreToolUse` hook denies any tool not on the definition's list and a `PostToolUse` hook records each performed effect for the disposition. The submission is the `StructuredOutput` tool with the definition's schema as `outputFormat`; `maxTurns` is the budget. `tools` is narrowed to the SDK's own tools the design allows — Read, Glob, Grep, Write and Edit on the twin's workspace directory, WebSearch under ZDR, Task — with **Bash and WebFetch off until the unit's egress is enforced at the network (slice 7), and then Bash only as a `code` step's tool inside a workflow, never the thread's** (ruled 2026-09-27). `CLAUDE_CONFIG_DIR` points at the twin's volume so every session file lands inside the key's boundary ([ADR-0007](0007-per-twin-encrypted-bundle.md) as amended). The wrapper that makes each result an execution — trigger, context, tools, one typed submission, handler, disposition, one audit entry — is unchanged; a definition now resolves to a `query()`'s options rather than to a tool runner's parameters. There is no `compactAfterTurns`; compaction is held off with `DISABLE_COMPACT=1` inside a day.

**Two shapes, one harness.** A drafting-shaped execution — drafting, extraction, the daily disclosure, a nudge — is a single-message `query()` with `persistSession: false`: one context, one submission, as before. The twin thread and an active workflow run are **streaming-input** `query()`s: one long-lived process fed by an inbox of user messages, which the SDK documents as the intended way to hold a conversation. **The twin thread is one session per rep per seat-local day.** The boundary is midnight in the rep's zone, never mid-conversation — a boundary that falls inside an exchange waits for a ten-minute idle gap; yesterday's tail is carried into the new session as one user message; compaction is off inside the day; old tool results stay in the context, and the API's server-side clearing turns on only if a measured day shows the thread losing crispness or coherence (ruled 2026-09-27). The spike's numbers, median and p95 time to first token: 2081/3594 ms for a fresh session's first turn, 1008/1455 ms for a later turn, 2131/2357 ms for a single-message execution; process start about 0.8 s on the spike's machine. **The seam's events** — a post landed, seen or settled; a run started, asked, finished or failed; an arrival; the rail's state — reach the thread as appended user messages, never a system-role message (which kills the child); `priority: 'later'` gives an event its own turn and `shouldQuery: false` appends without one. **Which events wake a turn is a code list**, ruled 2026-09-27: every landed post wakes one turn, so silence is the thread's decision and never code's default; a run's start, its asks and its end or failure wake; a run's steps and a post's being seen only append. A folded line is one result for two wakes — the SDK's own queueing, nothing to build.

**Three consequences for the automations.** (1) **An automation posts its own hand-off and never knocks or curates**: the twin thread alone knocks, spotlights, greets and comments, with `knock` and `spotlight` as its tools and the floors in code ([ADR-0031](0031-dashboard-notifies-twin-thread-is-a-pull-surface.md), [ADR-0044](0044-the-post-primitive.md) as amended). (2) **`arrival` is a turn of the thread**, not an automation with a definition of its own: the rep opening Inicio is an event; the welcome, the return line and the curation are the thread's submission; the occasion stays on the trigger record. (3) *Every unit of agentic work is an execution* stands, and *context never spans two* stands for the drafting shape; the thread's turns are the one place where executions share a context — the day's session — which is what the thread is for.

**Workflow runs** ([ADR-0012](0012-one-async-machine-per-app.md) as amended) are sessions of the same harness: a run is a session; an `agent` step is a `query()` with `resume`; `ask` and `wait` park the session id; `each` is `forkSession`. Decided, not built; the four first runs cut the slice.

**Approval keying** ([#294](https://github.com/Dito-Core/dito/issues/294), 2026-09-27, every check passed): the thread's «va» keys on the quoted message's stanza id, which resolves through one join to the draft; the dashboard's «Enviar» on the draft id; the dashboard's API acts on the post id; all 1:1 through `posts`, never through displayed text. A future `approve` tool of the thread receives the **draft id**, which the send lock already takes and the payload is bound to.

Conditions stated: ZDR on the key the unit uses ([ADR-0015](0015-one-model-provider-zdr-routed-ladder.md)); the two telemetry variables set in the child's environment; the SDK and the CLI it spawns pinned together in the runtime's image (0.3.283 / Claude Code 2.1.283 on the spike). The title and filename of this ADR stay as written, on purpose, as [ADR-0019](0019-deployment-envelope-six-egress-flows.md)'s do.

**Amendment 2026-10-06 (built: the day session, the events, the runs; one kind of definition).** The twin thread's day session is built ([#319](https://github.com/Dito-Core/dito/issues/319)): one row per twin per seat-local day, cut by code after a ten-minute idle gap past midnight, yesterday's tail carried in as twenty lines built from the doors' own records and never from the SDK's read API. Its events are a tenth occasion, `twin_thread_event`, and **which events wake a turn is a code list** as decided — widened since by the movements: a pick, a selection and a summons all wake ([#335](https://github.com/Dito-Core/dito/issues/335), [#341](https://github.com/Dito-Core/dito/issues/341), [#340](https://github.com/Dito-Core/dito/issues/340)). The thread alone knocks and curates ([#320](https://github.com/Dito-Core/dito/issues/320)); drafting's submission refuses a knock. Three sentences of the 2026-09-27 amendment read differently as built: the SDK's own tools are **absent** (`tools: []`, with Bash and WebFetch disallowed as a belt), the submission is a tool served on the in-process MCP server rather than `StructuredOutput` with an `outputFormat`, and no `PostToolUse` hook exists — the tool handlers record each performed effect themselves. Until the volume exists ([ADR-0001](0001-three-planes-twin-is-a-logical-entity.md)) the harness directory sits **beside the bundle in the clear**; FR-73 names it in every report as the recorded gap (spec #318 decision 3). The SDK is pinned at 0.3.288. **Workflow runs are built** ([#323](https://github.com/Dito-Core/dito/issues/323)): a run row, its step checkpoints and the clock store are opaque seam rows; the engine advances runs in the holder's pass right after the stream watch, behind the seat-state gate held twice — as a function and as the predicate inside every write; a run's session is opened once and every `agent` step is a wake on it; `run_step` is the eleventh occasion under the `request` mechanism; there is no pg-boss. Extraction and the disclosure still fire from the daily pass. **Decided 2026-10-06 (Diego), after reading another agent platform's documentation, whose custom agent calls its integrations as tools itself:** the `agent` step **holds every registered tool under that tool's own gate**, read or write, and calls them — the rule «an act is never the model's call mid-step» is withdrawn, `check` is withdrawn, `act` stays as an optional no-model call with mapped inputs, and `while` (a sequential repeat under a cap) and `end` (a successful end from inside a branch) join the kinds ([#324](https://github.com/Dito-Core/dito/issues/324)). **One kind of definition:** the six shipped automations — drafting, the thread, extraction, the daily disclosure, the nudge and the entity-kind question — become shipped workflow definitions fired by the trigger or schedule they already have, the older single-execution definition retires, and **one clock** fires every schedule from the store, the daily pass's own hour check going with it ([#357](https://github.com/Dito-Core/dito/issues/357)). *Every automation, Dito-shipped or rep-created, is an instance of that one shape* holds, the shape being the workflow definition; a rutina is a schedule or trigger wake plus a workflow definition, and a firing creates a run with the clock or the trigger as its creator ([#325](https://github.com/Dito-Core/dito/issues/325)).

**Amendment 2026-10-07 (decided: the agent step is agentic; one engine; the submission tools retire).** Ruled by Diego on 2026-10-07 after reading how another agent platform's custom agent works. **A turn ends when the model stops, and what it did is what it called.** Effects are gated tool calls and nothing else; the twin's words are the model's final message, streamed to the bar as they are written and committed to both doors with the turn's record; typed output, where a step declares it, is the SDK's structured output, stored as the step's outputs; a turn that says nothing and calls nothing is `no-action`. The eight submission tools — one per kind of execution — retire; the agent step is instructions, tools, an optional output schema, context recipes by name and a budget. This amends the 2026-08-26 text's *«the submission is the `StructuredOutput` tool»*: the submission as a tool the model must call goes, and the structured output the SDK provides is used as the SDK intends. **One engine.** Every definition runs through the runs engine's agent step: a run row and checkpoints for work that fires on its own (a schedule, a rep's rutina) even when it has one step, so it shows in Trabajos en curso; **no run row for a turn that answers someone** (the thread, drafting), which stays an execution. One setting on the definition says which conversation the step continues — *the day's conversation*, used by Dito's shipped thread only, or *fresh per run*; the thread's day session, its cut and its carried tail are unchanged. Dispositions keep their words and are derived from what happened — the effect's act word, `answered` for words or typed output, `no-action`, `asked`, `schema-miss`, `failed`. Built in three: [#357](https://github.com/Dito-Core/dito/issues/357) the engine, [#363](https://github.com/Dito-Core/dito/issues/363) the four conversations onto it (their submission tools retire), [#364](https://github.com/Dito-Core/dito/issues/364) the clock onto it — extraction, the disclosure and the reminders as shipped definitions with rows fired by the schedule store under preconditions — and the deletion of the older definition kind. [#326](https://github.com/Dito-Core/dito/issues/326) writes the workspace's two definitions on the new agent step.
