# Per-twin encrypted bundle; no shared plaintext index of rep content

All rep-twin memory — messages, chunks, embeddings, learned style, entity mirror, workspace metadata, run content — lives in **one SQLCipher-encrypted SQLite bundle per twin** (sqlite-vec inside). One named carve-out: pending questions are held aperture-side as twin-DEK ciphertext (ADR-0003) so disclosure never depends on the lease. Retrieval is twin-scoped: quantized vectors hot in RAM per active twin (≤ ~50MB target), exact scan, rescore against full-precision vectors decrypted on demand; ceiling ~100K vectors via conversation-window chunking. Cold start sits inside NFR-2: bundle open + hot-load p95 < 2s, LRU eviction. Descope/Olvidar delete rows and drop caches immediately; replica residue ages out within the bounded retention window, DEK-encrypted throughout. Forgotten-source citations degrade to *source-no-longer-held*.

Chosen over a per-twin Postgres schema with pgcrypto and over managed vector stores because erasure-by-key-destruction is the product's trust spine, and "your memory is one file that dies with one key" is only true if memory really is one file under one key. The stated ceilings are load-bearing and testable against the ADR-0028 fixture generator in the first slice.

**Amendment 2026-09-27 (the volume is the boundary; what the key is for).** *One SQLCipher file per twin* was the boundary when a twin was rows plus a bundle on a shared box ([ADR-0001](0001-three-planes-twin-is-a-logical-entity.md)). With the per-twin unit the boundary is the **twin's encrypted volume**, grafted onto the unit at assignment: the SQLCipher file; the Agent SDK's session files, which the SDK writes as plaintext JSONL inside the volume and nowhere else (ruled 2026-09-27 against mirroring them into the bundle through the SDK's session store, which only mirrors — it would double the writes and still leave the SDK's files on disk); and the workspace directory ([ADR-0011](0011-workspace-artifacts-immutable-versions.md) as amended). All under the twin's key, all in the FR-73 sweep, which extends to the volume. Retrieval stays twin-scoped as above. *Your memory is one file that dies with one key* becomes *one volume that dies with one key*, and stays true.

Stated because Diego asked whether encryption still buys anything once each twin is physically its own unit. **Isolation from a neighbour is now the unit's. The key buys three other things.** Erasure that reaches every copy at once — snapshots, backups, a disk the provider reuses — which is the only erasure a rep or a regulator can be shown ([ADR-0009](0009-erasure-is-kms-key-destruction.md)). A blast radius of one twin when a key leaks, where one key for the account exposes every twin. And a per-twin log of which role decrypted what, and when. Cloud block storage is encrypted by default under an account key, so *unencrypted* was never the alternative; *one key for all* was, and it gives none of the three. «We cannot read it» is a governance claim while Dito alone holds the key policy, and a cryptographic one only where [ADR-0008](0008-envelope-crypto-custody-of-two.md)'s second custodian is real — which is the condition on keeping the cost.

**Amendment 2026-10-06 (dated note: where the session files are until the volume exists).** There is no volume yet. The Agent SDK's session files — the day's and every run's — sit in a harness directory beside the bundle, in the clear, in the runtime's data directory; FR-73 names that directory in every report as the recorded gap (spec #318 decision 3), and the gap closes when the volume does ([ADR-0001](0001-three-planes-twin-is-a-logical-entity.md)). **A run's typed content** — its definition, inputs and every step's outputs — is a file sealed under the twin's key beside its session ([#323](https://github.com/Dito-Core/dito/issues/323)): *run content lives in the bundle* reads as *under the twin's key*, which it is; the run's three seam stores carry no content and are declared so. A rutina's content — its definition and the twin's sentence — lives in the bundle ([#325](https://github.com/Dito-Core/dito/issues/325)).
