# The wall is a deployment and credential boundary

Rep-side and owner-side are **separately deployed apps** — one monorepo, two deploy targets (triage clarification) — with disjoint IAM roles and disjoint DB users. The owner app's environment contains **no** credential that can name a bundle, a seam table, a rep S3 bucket, or a twin KMS key. The owner DB user is granted **named views with pinned column lists only**: finalized-fact Ledger views (whose definitions exclude `shadow` rows), a seats status view, grants, company sources, and its own state schema — adding an owner-visible column is a spine change. Rep-side is equally surgical: only the aperture role holds Ledger INSERT/UPDATE; other roles get grant-filtered views/functions. Every shared table carries `company_id` under Postgres RLS (sole exception: the global identity registry, ADR-0027). FR-71 verification is release-blocking in CI: an IAM-policy + DB-grant diff across both apps, and the standing adversarial refusal evaluation against the owner twin.

Chosen over a single app with code-level separation because the wall is the product's claim, and a code-convention wall is unprovable and erodes; retrofitting a credential boundary under a live system is a rewrite. The even-harder two-AWS-account split stays deliberately deferred until enterprise diligence demands it.

**Amendment 2026-09-09 (the second rep-side app).** The rep dashboard is a second app on the rep side (spec [#214](https://github.com/Dito-Core/dito/issues/214) decision 5; [#221](https://github.com/Dito-Core/dito/issues/221); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))), and the wall's letter applies to it as it applies across the wall. **rep-web holds no key**: no chain key, no twin key, no bundle path, no API key for a model, and it never imports the runtime — everything sealed or bundle-resident reaches it through the lease holder's API ([ADR-0010](0010-single-writer-lease.md) as amended). Its process starts from an **empty environment with an enumerated allowlist** — the list lives in code with a test asserting what is *not* in it, and the rig's launcher builds the same list by hand — because a named blocklist cannot say anything about an environment nobody enumerated. Its role, `dito_rep_web`, holds **column-level grants pinned in one clause** that FR-71a's check re-derives, with a grant planted on a sealed column (the directory's name) proven red in CI; it may mint a tap and a send command ([ADR-0006](0006-send-lock-topology.md)), consume an invitation, append an acknowledgment, and write two columns of its own seat, and nothing on `posts`, the disclosure lines, a key table or a Ledger object. The SES credential it sends with is the one residual, argued in [ADR-0022](0022-system-outbound-rails-closed-notify-catalog.md) as amended.
