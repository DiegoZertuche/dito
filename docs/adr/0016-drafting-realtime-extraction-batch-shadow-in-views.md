# Drafting real-time; extraction batch; shadow lives in the view grants; the rep is the labeler

Inbound → classify → draft inside the ~1-min NFR-2 budget, cold start included. Extraction is a daily per-chat Batch-API job cut ahead of the disclosure. Shadow mode is a row flag whose filter lives **inside the finalized-view definitions** — the only Ledger objects the owner DB user holds — so twin, dashboard, API, and export are gated identically at the grant level; the launch gate flips the flag, never rebuilds the pipeline. NFR-3 ground truth = rep corrections/confirmations on shadow-fact disclosures — the rep is the labeler, inside the wall. **No standing operator access to bundle content, mechanized**: no bundle-reading operator tooling exists; production shell access only via audited sessions (SSM) feeding the ADR-0020 chain; break-glass exists only as a rep-consent flow — explicit, time-boxed, recorded in the audit chain.

Chosen so precision measurement never requires bundle reads and operator access is enforced, not posture. **Open detail** (named at triage, no ticket): the break-glass consent-flow *shape* is an assumption, resolved just-in-time when a pilot-era slice forces it; the invariant above stands regardless.

**Amendment 2026-08-30 (the budget measures the twin's work; the settle window sits before it).** "Inbound → classify → draft inside the ~1-min NFR-2 budget" is narrowed: the budget is the interval from **when the runtime takes a conversational turn up** to when its draft is ready, and it still includes cold start. It no longer starts at the arrival of the first message of that turn, because **drafting now waits for the chat to go quiet** ([#75](https://github.com/Dito-Core/dito/issues/75), from the 2026-08-30 rig session): firing once per inbound message produced three drafts for a customer who typed three short lines — *"this causes too much churn to the rep"* — and the remedy Diego specified is a settle window of roughly one to two minutes, ceilinged so a chatty customer cannot defer a draft forever.

The window is a **deliberate product wait, not latency**, and the distinction is the whole point: what the budget exists to bound is the twin being slow, and a twin that answers a half-finished request fast is worse than one that waits for the request to finish. Batching also moves the budget in the right direction on its own terms — the same three messages now cost **one** model call instead of three, so the work inside the budget is a third of what it was.

Both numbers stay measurable and neither is hidden: `draft_timings` keeps `event_received_at` at the turn's **oldest** arrival, so the total the customer experienced is still in the record, and `runtime_seen_at` marks pick-up, so `draft_ready_at - runtime_seen_at` is the budget above and the gap below it is the settle window plus poll latency. **Extraction is untouched** — still a daily batch cut ahead of the disclosure, still off the latency path.


**Amendment 2026-09-02 (the launch gate is a per-company act).** "The launch gate flips the flag" is now a mechanism, decided at the slice-4 grilling ([#112](https://github.com/Dito-Core/dito/issues/112), spec [#126](https://github.com/Dito-Core/dito/issues/126)). The flag stays a row flag and the filter stays inside the view definitions; what changes is how the flag is set. A minimal `companies` registry carries `shadow_lifted_at`, and **the aperture stamps `shadow` at filing from the company's mode** — `true` while unlifted, `false` after — so facts filed after a lift land visible without anyone touching them. **Lifting is one audited act per company**: set the timestamp and flip that company's existing entity and fact rows, in one transaction, chained under [ADR-0020](0020-hash-chained-audit-log.md), refusing to run twice. On the rig it is a break-glass script the developer runs over their own traffic; for a real owner it is the same act, gated by Test 4's precision measurement rather than by a person's judgement. The rig owner and a future real owner go through the same door.

Rejected: a one-off `UPDATE` (the steering surface goes stale the next day, when new facts arrive shadow), and a dev-owner bypass reading shadow rows (breaks "twin, dashboard, API and export gated identically at the grant level" above, and steers a surface no real owner will ever see). Known consequence: [ADR-0038](0038-the-customer-asking-and-the-business-agreeing-are-two-facts.md)'s payload-migration window closes for a company the moment it lifts, exactly as it would at launch.

**Amendment 2026-09-06 (extraction is the batch lane's; one attempt per occasion per day).** «A daily per-chat Batch-API job» has meant, since slice 5a, one execution per chat on the **batch lane** of the one holder ([ADR-0010](0010-single-writer-lease.md) as amended) — the runtime's own concurrency, never Anthropic's Batches API, which was not adopted: an extraction that looks ([ADR-0039](0039-the-twin-asks-only-what-the-rep-can-settle.md) as amended) is a tool loop, and a tool loop is not a batch request. The cut ahead of the disclosure stands — extraction settles, then the post — and the request wake ([ADR-0014](0014-runtime-harness-tool-runner.md) as amended) fires the same definition on demand without stopping the runtime. What slice 5b ([#179](https://github.com/Dito-Core/dito/issues/179), spec [#193](https://github.com/Dito-Core/dito/issues/193)) decided about failure: **a failed batch execution is recorded and the lane moves on.** The execution record and its chain entry are written with the spend the model call really cost; the claim row settles `failed` beside `filed` and `deferred`; the chat is not tried again that day; and the next day's pass, which already reaches back seven days for anything unfiled, extracts it a day late — nothing is lost, and one bad chat cannot silence the day, because the disclosure's precondition counts a failed run as settled. The disclosure execution keeps the same rule: one attempt per occasion per day, a failed post leaves its lines pending for the next day's post, and no fact finalizes unseen because the correction window starts at reachability ([ADR-0004](0004-push-only-crossing.md)). The realtime lane keeps its fail-stop and replay; its attempt cap stays the horizon's, slice 7's.

**Amendment 2026-09-09 (the realtime lane records a failed execution too; one occasion keeps the stop).** The last sentence of the 2026-09-06 amendment — *the realtime lane keeps its fail-stop and replay; its attempt cap stays the horizon's* — is overturned for drafting and the twin thread, ruled at the slice-6a boundary after a thread execution over three old self-chat rows exhausted its budget and killed the runtime on link day ([#225](https://github.com/Dito-Core/dito/issues/225) F1; built as [#240](https://github.com/Dito-Core/dito/issues/240)). The rule is now one rule for both lanes, in [ADR-0042](0042-opaque-deliveries-are-seam-rows.md)'s words: **an execution that fails on what it was handed — a budget exhausted, a refusal chain, a tool or the model client throwing on its input — is recorded with its failure and its chain entry, and the lane goes on; fail-stop is for infrastructure** — the seam refusing, the bundle unopenable, the key unavailable. What differs between the lanes is what a failure consumes. A batch failure settles its claim row and tomorrow's window reaches back over the messages, so nothing is lost; a realtime failure consumes its trigger, so the turn the model could not finish gets no second attempt and the rep reads nothing about it — one paid attempt per trigger, which is the bound that replaced the cap. **One realtime occasion keeps the stop: the entity-kind classification.** Its trigger is the rep's own confirmation, and the crossing that follows reads that confirmation from the marker the thread wrote — so consuming it under a failure word would lose the crossing until the rep confirmed again, and marking it confirmed with nothing crossed would leave audit coverage red. A refused classification therefore still stops the holder, and the next start asks it again from the uncrossed binding; what would lift it is a per-process attempt bound like the disclosure's, and that stays the horizon's ([#117](https://github.com/Dito-Core/dito/issues/117)).
