# Send lock topology: one taps table, two minters, two send classes

Two send classes, enforced by the plane's executor. **`customer_send`** (any JID except self) requires a `send_commands` row referencing a recorded tap. Taps live in one rep-side Postgres `taps` table with `UNIQUE(draft_id)` — the constraint *is* the cross-surface single-use lock; tap row + send_command row are written in one transaction; late losers get "ya se envió." Exactly two non-model code paths may insert taps: (a) rep-web's authz layer (dashboard taps, approval-card redemptions), (b) the quoted-reply affirmation matcher, whose input is pinned to the raw plane-delivered event — never any model-produced value. **`system_send`** is permitted only to the rep's own self-chat JID, where "self" derives exclusively from the live whatsmeow session identity inside the plane — never from a table or caller value. Approval-card deep links are per-draft, single-use, signed, short-expiry, dead at seat end. Send outcomes are sent(acked) / failed / unknown→held — never silent, never auto-retried; retry is a new tap. FR-70's audit is the SQL join over this table; an outbound with no command row is a sev-1.

Chosen because no code or model path may reach a customer without a recorded human tap, and a database constraint beats any application-level dedupe.

**Amendment 2026-09-09 (the second minter is realized).** Path (a) above exists ([#224](https://github.com/Dito-Core/dito/issues/224); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))): the dashboard's **Enviar** writes the tap row and the `customer_send` command **in one transaction under `dito_rep_web`**, the plane's executor sends as before, and a late second press meets `UNIQUE(draft_id)` and reads «ya se envió» — FR-70's join is green with two minters present, and the `taps` CHECK names both. The lock's code moved into the seam package, parameterized by the recorder of its refusals, so the two minters run one implementation rather than two copies. One consequence for [ADR-0020](0020-hash-chained-audit-log.md): a refusal recorded by a keyless minter — rep-web holds no chain key — is chained by the lease holder at its next pass, so the entry is owed rather than immediate, and the refusal row is what carries it until then. The approval-card deep links this ADR describes are not built: the card is a page behind a login, and the tap is a button on it.

**Amendment 2026-10-02 (an approval is keyed to one effect, and never stands).** Stated for the record, from the dots recon ([#310](https://github.com/Dito-Core/dito/issues/310), R1) and the code check that preceded it ([#294](https://github.com/Dito-Core/dito/issues/294), 2026-09-27, every check passed): an approval is keyed to one effect's stable id — a «va» to the quoted message's stanza id, which resolves through one join to the draft; «Enviar» to the draft id; a card's act to the post id — resolved by code from the quote or the card and never from a model-supplied value, with the **draft id** the canonical spelling for a send because the lock already takes it and the payload is bound to it. Continuation, delegation and a later run never inherit an approval, and there is no standing permission: a second send is a second tap. This records the rule the two minters already keep; it adds no check (Diego, 2026-09-29: agentic first).
