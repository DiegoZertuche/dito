# One async machine per app; pinned envelope; seat-state gate on every commit point

Triggers, scheduled runs, and workflows share **one machine** — durable run + checkpointed steps + pg-boss — instantiated per app over that app's normalized `integration_events` ingress. The envelope is pinned: plaintext metadata `(source, external_event_id, type ∈ versioned registry, company/seat/twin ids, occurred_at)` + ciphertext payload where rep content; delivery is at-least-once with consumer dedupe on `(source, external_event_id)`. Non-plane rep-side adapters persist metadata + a provider reference only — never content; content is fetched by the lease holder at wake (**pull-on-wake**; ADR-0008 custody unchanged). Wake predicates use a metadata-only vocabulary; content-conditioned wakes are two-stage (metadata wake → lease-holder evaluation); predicate rows carry no names or text and are hard-deleted at automation deletion and seat retirement. Run *content* lives in the bundle (rep) or owner tables (owner); coordination rows are opaque. Guidance folds at step boundaries; runs never restart; pause/cancel are distinct flags. **Every wake, step boundary, send-command write, and finalization tick consults seat state** (active | enforcement-paused | closing | retired) — one central gate, written only by the seat-lifecycle service (ADR-0027). Ledger-derived context is re-fetched through grant-filtered tools at every step boundary; checkpoints store fact references, not fact content. Primitive definitions are declarative, serializable specs carrying a schema version (as does the surface-registry snapshot); consumers enforce min-reader/max-writer compatibility and fail closed to the lesser affordance set. Internal sub-loops are permitted (same harness, same twin, nothing user-named); rooms containing the owner twin and multi-employer personas are prohibited. Progress streams via SSE. **Sessions are threads of this same machine**: boundaries twin-cut (model-classified, rep-correctable by a sentence, never rep-managed); session state lives twin-side in the bundle; a session partitions attention and task context, never memory.

Chosen because divergent trigger/run/workflow implementations are the week-one failure mode of a two-app system, and run state in RAM dies on lease flips.

**Amendment 2026-09-27 (the machine's session is the Agent SDK's).** The last sentence above — *sessions are threads of this same machine* — was a promise without a mechanism; the harness now has one ([ADR-0014](0014-runtime-harness-tool-runner.md) as amended). **A session is an Agent SDK session.** The twin thread's is one per rep per seat-local day. **A workflow run is a session of its own**, its steps typed — `agent` (a `query()` with `resume` on the run's session), `code`, `act` (a gated tool), `ask` and `wait` (the run parks its session id and the rep's answer or the awaited event resumes it — the suspension [ADR-0044](0044-the-post-primitive.md) owes), `post`, `each` (`forkSession` per item), `if`, `check` — with **run rows and step checkpoints as opaque seam rows** carrying metadata only and run content in the bundle, exactly as the rule above says; a definition's versions are draft, pending and active (FR-75). Guidance still folds at step boundaries (`steer_run`); pause and cancel are still flags; runs never restart; the seat-state gate is consulted at every wake and step boundary. The twin thread starts, steers and reads runs; progress reaches the rep through Trabajos en curso by code, and the thread wakes on a run's start, its asks and its end, never its steps (ruled 2026-09-27). **The thread's session boundaries are no longer *twin-cut, model-classified*:** they are the seat-local day, cut by code at midnight in the rep's zone and never mid-conversation; *rep-correctable by a sentence* becomes *searchable by a sentence*, through `search_messages` over the archived sessions. Decided, not built; the four first runs cut the slice.

**Amendment 2026-10-06 (built: the machine is rows and the pass).** The run is built as decided ([#323](https://github.com/Dito-Core/dito/issues/323)): **a durable run row, checkpointed steps and a clock store**, all opaque seam rows, read and advanced by the holder's own pass every two seconds — **there is no pg-boss** (the architecture's §7.6: *Engine. None*), and progress does not stream: Trabajos en curso is a server-rendered read. Seven step kinds are built — `agent`, `code`, `act`, `post`, `wait`, `if`, `check` — guidance folds at step boundaries (`steer_run` appends to the run's session and the next `agent` step reads it), pause and cancel are flags, and **runs never restart**: a run a new process finds `running` ends `failed` with its report. Two sentences above are reversed by what was built. *Run content lives in the bundle* — it lives in the run's own Agent SDK session file and in a content file sealed under the twin's key beside it, in the harness directory, never in the SQLCipher bundle; the seam rows carry ids, closed words, counts and instants only. *Seat state (active | enforcement-paused | closing | retired)* — the gate reads the seam's three states, invited, linked and retired; only `linked` advances, and the gate is one function plus one SQL predicate re-asserted inside every write, where the pause state of an automation joins it. The 2026-09-27 amendment's *decided, not built* on the day session and on `search_messages` closed with [#319](https://github.com/Dito-Core/dito/issues/319) and [#320](https://github.com/Dito-Core/dito/issues/320): the day is cut by code and searched by a sentence over the bundle's own store of the day's lines, never over the SDK's files. **Decided 2026-10-06 (Diego):** the `agent` step holds every registered tool under its own gate and calls them itself; `check` is withdrawn and `act` becomes optional; `while` repeats in sequence under a cap and `end` ends a run from inside a branch; `each` forks the session by copying the parent's session file under the child's id, one child run per item, a failed child leaving its siblings alone ([#324](https://github.com/Dito-Core/dito/issues/324); FR-75's versions are [#325](https://github.com/Dito-Core/dito/issues/325)'s). The six shipped automations join this machine as one-step workflows and the older definition retires ([#357](https://github.com/Dito-Core/dito/issues/357)) — *triggers, scheduled runs, and workflows share one machine* becomes literally true there.

**Amendment 2026-10-08 (built: nothing the rep asked lives in memory).** [#358](https://github.com/Dito-Core/dito/issues/358) (PR #372): a pick on a card, a selection and a summons are rows (`rep_asks`, keyed by the id the dashboard minted, sealed where they carry the twin's or the card's words) with a processing marker in the shape of the typed line's, read by the pass after the typed lines and served through the same path, the marker written inside the turn's transaction — so each is answered once across a restart; the arrival's write-only marker (`rep_arrival_executions`) is promoted to the marker the pass reads. The in-memory raise remains only for what the ticket keeps ephemeral (`post.landed`, `post.settled`, `post.seen`, `rail`, `run.*`, `expiring`). **A turn's record says when the session granted it**, not when its wake was handed over: a rep's line at the hand-over when the session was idle or when the turn ahead ended, before the model is called; an event's turn (a `later` wake) at its first frame, since the child runs a line that arrives beside it first — so two turns queued on one day session record in the order they ran. And the turns of one pass reach the day session **in the order the pass raised them**, by construction: each takes its place when it is submitted and hands its wake over only after the one before it has (a hand-over order on the pass; only the hand-over is ordered, the lane still admits four), so a rep who types a line and then picks a card is answered in that order.

**Amendment 2026-10-11 (a run's start appends; a rutina fires from the ask).** The 2026-09-27 amendment's «the thread wakes on a run's start, its asks and its end» is amended by the boundary (boundary [#327](https://github.com/Dito-Core/dito/issues/327)): **a run's start appends and wakes nothing** — the turn that started it already told the rep and a run a rutina fired is on Trabajos en curso — while its asks and its end or failure still wake ([#382](https://github.com/Dito-Core/dito/issues/382), PR #383). And a rutina the rep asked for is **active the moment the twin writes it**, its first firing the next instant at or after the ask — the clock's rule that an instant before activation never fires, unchanged ([#386](https://github.com/Dito-Core/dito/issues/386), PR #388; Diego 2026-10-11).
