# The twin asks the rep only what the rep's answer can settle

**Every rep-facing ask must be proactive about the rep's work, never maintenance of ours.** Diego, reading a question on his phone during the 2026-08-30 rig session: *"Every time we present something to the user it should be to be proactive about something of their work, not to fix our system."* Asking a rep to remember what a customer ordered last month is the system requesting its own lookup. It is work created, not work saved — and it is charged against the one budget this product cannot overspend, which is the rep's attention (ADR-0036).

**The operative test is narrower than "proactive", and it is the one to apply: can the rep's answer settle the thing?** A question is legitimate only when the sentence it shows is *complete* — so that a «si» leaves a record that means something, and a «no» leaves nothing. The twin had two routes into the question surface and they fall on opposite sides of that line. A **below-threshold** candidate passes: the sentence is whole and the rep is confirming whether it is *true*, which is knowledge only the rep has. An **unresolved reference** fails: the extractor read «me mandas lo mismo del pedido pasado?», could not tell what «lo mismo» named, and asked anyway — so a «si» would have filed *«Te pidió lo mismo del pedido pasado»*, a sentence still unresolved after the rep answered it. The question's shape was yes/no; the uncertainty's shape was a missing **value**. Answering could not fix it, which is why the rep's reaction to it was *"not even sure what is even asking"*. The same test admits the entity-attachment ask, which names a whole thing the rep alone can confirm.

**So an unresolved reference is dropped: no fact, no question, no line.** Dropping is the safe direction — FR-31 buys precision with recall, and a reference the twin cannot resolve is a fact it cannot honestly record. The drop is **counted** rather than silent, because a remedy whose cost is invisible cannot be argued about later.

**This reverses a decision taken three days earlier, and the reversal is narrower than it looks.** [#66](https://github.com/Dito-Core/dito/issues/66) measured the confidence gate and found it inert: every wrong crossing arrived at 0.95–1.00, and the middle band held one of 88 graded candidates. That diagnosis stands, and the categorical `reading` it introduced stands with it — `stated` versus `unresolved_reference` is exactly the distinction the gate could not see, and it is **kept**, because it is what makes either remedy expressible. What #66 got wrong was only the *destination*: it routed the new reading to the rep, when the reading names a lookup the twin should do itself. The classification was right; the exit was wrong.

**The twin owes itself the answer it was asking for.** «lo mismo del pedido pasado» is precisely what thread retrieval exists to resolve, and drafting already has it while extraction has none. The full remedy is extraction becoming an execution with tools — nothing preloaded, the agent free to search the thread and other surfaces (ADR-0037's execution shape) — and it waits on the execution runtime. Until then the interim is **drop, not ask**, and the interim must not be quietly widened into a bolted-on retrieval call, because the cheap version buys the behaviour while forfeiting the architecture that made it correct.

Chosen because a question is a claim about whose knowledge is missing, and the twin had that backwards: it asked the rep for something it could have looked up, in a shape the rep could not answer. **A surface that may interrupt the rep at all is only worth having if it never spends that permission on our own uncertainty** — so every future ask gets the same test before it ships, including the ones that pass it today.

**Amendment 2026-09-06 (the twin looks first; a resolved candidate may become a question).** The full remedy the fifth paragraph named has landed ([#196](https://github.com/Dito-Core/dito/issues/196), spec [#193](https://github.com/Dito-Core/dito/issues/193)): extraction is an execution with three read tools — the rep's history by meaning, the bound chats, the lines already filed for one customer — and it **looks before it decides**. «me mandas lo mismo del pedido pasado?» makes it search that chat's history; «mándame lo mismo que a Torres» resolves in another customer's conversation, because the rep's whole history is the scope. *Resolved* means exactly one referent, wherever it was found: the candidate then carries the goods the referent named, under a third reading, `resolved_reference`, and the aperture files it **exactly as it files a stated one** — same threshold, same question route — because the sentence is now whole and a «si» settles something. That is the test above applied, not relaxed: what changed is not the rule about questions but which candidates are complete. Two referents that differ, or none, are still `unresolved_reference`, still dropped, still counted — a guess between two orders would put a wrong one in the rep's name. The rep is owed the difference between a line read off the day and one arrived at by looking, and gets it as a **mark rendered by code from the reading** — «(por referencia)» — that names no order, no chat and no customer: the referent is the one thing the mark may never carry, because owner-visible provenance stays the day's own message ([ADR-0004](0004-push-only-crossing.md)), and nothing about it is stored anywhere — not in the payload, not on the line, not on the run row, which counts resolutions only so the price of looking has a denominator. Looking never changes whose message a fact belongs to, and it never pairs across days ([ADR-0038](0038-the-customer-asking-and-the-business-agreeing-are-two-facts.md) as amended). The interim — drop, not ask — is over, and the bolted-on retrieval call the paragraph refused was never built.

**Amendment 2026-09-09 (the test is the principle; the question route is closed).** [ADR-0043](0043-a-question-is-a-service-never-a-plea.md) sets the test this ADR's second paragraph left one step short: *can the rep's answer settle the thing* asked whether the rep **could** answer, and a below-threshold candidate passed it — the sentence is whole and the rep knows whether it is true. It never asked whether answering was the rep's work or ours. It was ours: a confidence number is a fact about the extractor, and every question the gate produced spent the rep's attention on the system's uncertainty — the failure this ADR's first paragraph named, arriving through the route it had let stand. So the operative test is now **the twin asks only when the answer makes the rep's own work smaller, and never to fill a hole in the record**, applied first; *can the answer settle it* remains necessary and is no longer sufficient. The 2026-09-06 amendment's clause that a resolved candidate «may become a question» is **superseded**: a `resolved_reference` candidate above the gate files exactly as a stated one, and below the gate it drops exactly as a stated one — the same `below_threshold` count, no fact, no question, no line. Everything else in that amendment stands: the twin looks first, *resolved* means one referent, two that differ are unresolved and dropped, and the «(por referencia)» mark is rendered by code. The entity-attachment ask survives on its own footing as the binding question — one of the two acts reserved to the rep, not a hole in the record.

**Amendment 2026-10-02 (the hint: two chats under one name are an ask again when code can tell them apart).** Since slice 5a ([#175](https://github.com/Dito-Core/dito/issues/175), Codex round 2) the drafting lookup has shown the twin a reference and a confirmed name per chat and nothing else — never an address, never content — so that no model can address a send; and two confirmed chats whose names fold to one label were ruled **not an ask**: «¿Torres o Torres?» is a choice the rep cannot knowingly make, so the lookup served no reference and the twin could only say what it found. The 6b boundary ([#270](https://github.com/Dito-Core/dito/issues/270), finding F8) met the case that rule did not foresee — one customer with two numbers, and a rep saying «el que sea» — and the honest sentence blocked the rep's explicit instruction. Ruled by Diego on 2026-09-27 and built as [#300](https://github.com/Dito-Core/dito/issues/300) (PR #301): when names collide, each candidate carries a **hint** rendered by code from facts the twin may see without seeing an address — the number's last four digits and the day the other side last wrote — and with it the two are an ask again, under this ADR's own test: the rep can settle «¿el que termina en 8416 o el que te escribió el 12?», and «el que sea» yields a draft to one of them with the twin's line saying which, by its hint. The twin says the hint in the rep's register; the rep answers in prose, and a pick by hint, by position or by «el que sea» is the model's reading, never a keyword. **So «not an ask» narrows**: a name matching more than one chat is not asked about only when the name and the hint read the same across them, or when a hinted chat has no part of its hint that is its own — those still get the honest sentence, which now names the digits and the day too. Where nothing collides, nothing changed. One remainder stays recorded on #300: a hint or «el que sea» in the rep's first message still costs one question, because a draft to an unsettled chat is refused structurally and lifting that is a rule about every ask, not only same-name ones.

**Amendment 2026-10-02 (one stable reference per customer — decided 2026-09-28, applied in the harness slice).** A reference to a customer becomes the entity's own stable id, never a number minted per run (the agent architecture, D15, ruled by Diego on 2026-09-28; built in the harness slice, [#315](https://github.com/Dito-Core/dito/issues/315)). Two consequences for the ask. The answer to one — «el segundo», «el de 8416» — resolves against ids the twin already holds, so the focus no longer re-serves candidates for identity and the guard no longer matches the twin's words against hint keys; the one check left is that an id names a row. And a customer with two numbers is **one reference**: the twin picks the chat when it writes, the draft card shows the number's tail and the tap covers the pick, so the «which chat» ask of the amendment above is put only when the twin has no basis to pick. This ADR's test is untouched; what changes is how few asks reach it.
