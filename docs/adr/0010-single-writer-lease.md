# Single-writer lease; twin affinity

A Postgres lease maps each rep twin to exactly one runtime process; **all** bundle-touching work — sessions, workflow steps, extraction prep, dashboard reads — routes to the lease holder. Dashboards are clients of that service's authenticated API; they never touch bundles, blobs, or DEKs directly.

Chosen so two processes can never write one bundle, DEKs stay out of processes that don't need them, and dashboards can't grow direct store access.

**Amendment 2026-09-04 (two lanes inside the one holder).** No lease exists yet: the runtime is one process that opens the twin's bundle at start and holds it for its life, and it has done all bundle work in one sequential loop — so a long run blocks a short one, which is why the rig's extraction script asks for the runner to be stopped first. Slice 5a ([#113](https://github.com/Dito-Core/dito/issues/113), spec [#171](https://github.com/Dito-Core/dito/issues/171)) had to decide what happens when extraction, given tools, holds twin memory for minutes while a customer waits for a draft; the boundary input named a lease per step, a read snapshot, or a change to this ADR. None of the three. The rule above says all bundle-touching work routes to the one holder; it does not say the holder does one thing at a time, and the block was an artifact of the loop, not of the rule. **The holder runs executions concurrently, in two lanes**: a realtime lane (drafting, the twin thread, the entity-kind classification) and a batch lane (extraction, the daily disclosure), the batch lane capped at one execution at a time so it never starves the realtime lane of model or bundle time. A bundle statement is atomic and synchronous, so executions interleave at their model calls, where the minutes go; bundle writes stay short transactions. This is [ADR-0016](0016-drafting-realtime-extraction-batch-shadow-in-views.md)'s realtime/batch split made literal inside one process — *same runtime, different runs* — and it changes nothing across processes: two processes still never hold one bundle, and the process-level lease, with its flips and its fleet placement ([ADR-0018](0018-fleet-scaling-by-lease.md)), stays where slice 7 has it. An operator who wants a batch run now asks the running runtime for it through the request wake ([ADR-0014](0014-runtime-harness-tool-runner.md) as amended) rather than stopping it.

Rejected: a lease per step presumes lease machinery that does not exist and would be built twice; a read snapshot breaks semantic search, which needs the bundle's embedding index, and would hand extraction a stale view of the chat mid-day; a multi-writer bundle is the one thing this ADR exists to forbid.

**Amendment 2026-09-05 (what a lane does not guarantee).** A lane bounds how many executions run at once; it does not order two that touch one target. All three slice-5a build tickets met the same shape and recorded it rather than building around it ([#174](https://github.com/Dito-Core/dito/issues/174), [#175](https://github.com/Dito-Core/dito/issues/175), [#176](https://github.com/Dito-Core/dito/issues/176); ruled at [#177](https://github.com/Dito-Core/dito/issues/177)): a later «va» can race an earlier prose dismissal of the same draft; two opposite answers to one aperture question are settled by whichever model call reaches the aperture first; two rep messages in one pass both read the focus and the later finisher writes it; two confirmations of one chat both classify its kind. In every case the unsafe interleaving needs a tool's read to land inside a millisecond-long transaction that began after a multi-second model call, so the realistic ordering is the safe one, and where the race is reachable its outcome is the rep's most recent instruction or an idempotent write. **Decided, not built:** whether the holder owes per-target ordering — a sequencer over the target, or a per-draft lock the send lock and the tools share — is a decision about what the lane guarantees, recorded on the horizon ([#117](https://github.com/Dito-Core/dito/issues/117)). Until it is taken, a write that summarizes what the rep last said (the focus) may prefer the rep's message instant to the execution's finish, so the last *message* wins rather than the last *finisher*.

**Amendment 2026-09-06 (what the batch lane does on a failure; what one execution does with one connection).** Two notes from slice 5b ([#179](https://github.com/Dito-Core/dito/issues/179), spec [#193](https://github.com/Dito-Core/dito/issues/193)). The batch lane **does not stop on a failed execution**: the run is recorded `failed` with its entry and its real spend, and the lane takes the next chat — the fail-stop belongs to the realtime lane, for a seam it cannot read, and a chat the model could not finish is not that ([ADR-0016](0016-drafting-realtime-extraction-batch-shadow-in-views.md) as amended). And inside one execution, the tools that touch that execution's own Postgres connection run **one at a time** ([#195](https://github.com/Dito-Core/dito/issues/195), [#205](https://github.com/Dito-Core/dito/issues/205)): the SDK's tool runner executes every tool call of one model response concurrently, two savepointed tools on one connection then share one savepoint stack, and a release for one destroyed the other's — an execution that left no record. The queue is a fact about how the runner runs tools and lives beside it, in the execution package; each side keeps its own savepoint wrapper on its own connection, the owner twin's included, because the wall ([ADR-0002](0002-wall-is-a-deployment-and-credential-boundary.md)) forbids sharing more. Bundle-only tools need no queue, and two executions on two connections never wait on each other — which is the concurrency the 2026-09-04 amendment promised, kept.

**Amendment 2026-09-09 (the API exists; what the realtime lane does on a failure).** The sentence above — *dashboards are clients of that service's authenticated API* — is built (spec [#214](https://github.com/Dito-Core/dito/issues/214) decision 5; [#221](https://github.com/Dito-Core/dito/issues/221)–[#224](https://github.com/Dito-Core/dito/issues/224); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))). The holder serves a **local API on loopback behind a bearer** the dashboard alone holds: **reads** — the rail's state, the link credential, the chat directory with names opened, the feed — and **acts** — scope a chat in or out, dismiss a draft, retract a line, confirm or decline a binding, ask for a pairing code — with every route, its method and its refusal words pinned in the seam package so the two sides cannot drift. Every act is an execution with a `dashboard` trigger ([ADR-0014](0014-runtime-harness-tool-runner.md) as amended), the gate stands in front of the act and not only the page, and the holder is the one writer of the seat's `linked` flip, from the rail's own row. What the dashboard may reach without the holder is exactly what is plaintext on the seam under its own role — sessions, the tap it mints, the fill's progress — so the dashboard opens with the holder down and says so. And the 2026-09-06 amendment's rule for the batch lane now holds for the realtime lane too, ruled at the boundary after an execution failure killed the runtime on the rig (([#225](https://github.com/Dito-Core/dito/issues/225)) F1; built as [#240](https://github.com/Dito-Core/dito/issues/240)): **an execution that fails because of what it was handed — a budget exhausted, a refusal chain, a tool or the model client throwing on its input — is recorded with its failure and its trigger consumed, and the loop goes on. Fail-stop is for infrastructure**: the seam refusing, the bundle unopenable, the key unavailable — [ADR-0042](0042-opaque-deliveries-are-seam-rows.md)'s rule, carried from the plane to the holder. A poison row that fail-stopped the runtime was a dead rail for every chat; a poison row recorded is one execution the rep never sees. The entity-kind classification is the one realtime occasion that keeps the stop — [ADR-0016](0016-drafting-realtime-extraction-batch-shadow-in-views.md) as amended says why — and its bound stays the horizon's.

**Amendment 2026-09-27 (the lease and the unit).** *A Postgres lease maps each rep twin to exactly one runtime process* stands, and the process is now the per-twin unit ([ADR-0001](0001-three-planes-twin-is-a-logical-entity.md) as amended): the lease says **which unit holds this twin's volume**, and a flip is a suspend, a graft and a wake. Everything routed to the holder above is still routed to it — the two lanes run inside the unit, the local API is served from it to rep-web, the realtime lane's rule on a failed execution is unchanged — and the one writer of a bundle is the one unit that has the volume. The dashboard remains a client of the unit's API and never touches the volume.

**Amendment 2026-10-06 (built: the lane drives runs).** A run's steps are driven on the **batch lane** ([#323](https://github.com/Dito-Core/dito/issues/323)): the pass claims a run, submits its drive to the lane, and a run whose step fails ends `failed` with its report in its own task while the lane goes on — the fail-and-move-on rule of 2026-09-06, applied to runs. The local API gains the read `/runs` and the acts pause, resume and cancel; the holder alone writes the run row, the step checkpoints and the clock store (delete revoked even to itself), and rep-web reads runs only through the API. The reads behind the bearer have grown since 2026-09-09 — the canvas, the arrival, the seen marks, the day's exchanges, the notepad, the working memory, the card notes, the corrections — all under the same rule.

**Amendment 2026-10-08 (built: the clock store keeps its rows).** [#364](https://github.com/Dito-Core/dito/issues/364) (PR #370) found that a rutina's cadence row left by cascade when its `automations` row was deleted, around this ADR's revoke. The foreign key is RESTRICT now, Descartar and Activar mark a cadence row ended, `last_fired_at` stays readable, and Dito's own rows are never ended by the rep.
