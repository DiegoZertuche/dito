# A closed four-class effect taxonomy; automation turns are enveloped

Every externally-visible effect is exactly one of four classes; anything unclassifiable defaults to class 1. **(1) Communications to third parties** — never directly executable from any model tool surface, on any transport: an integration action whose effect delivers a message to a third party is class 1 *regardless of provider* and may appear only as a draft-terminating proposal behind the ADR-0006 tap. **(2) Ledger writes** — aperture only (ADR-0003). **(3) Non-communicating state mutations through rep-connected tools** (defined by exclusion): exposed only in live-rep-command contexts or automations in `active` state; every invocation writes an intent record before execution (at-most-once across lease flips; unresolved outcomes land unknown→held; retry explicit); audit-chained. **(4) System notifications** — only via the notify service (ADR-0022); notify is never present on any model tool surface in either app. Every automation-origin turn is tagged where context is assembled — never presented as the human.

Chosen so prompt injection can never reach an outbound effect and no send-capable tool can ride "CRM writes" into an automation.

**Open clause** (split at triage): *how* integration actions get send-classified at connect time — the capability-typing mechanism behind the class-1/class-3 sort — is an open decision, tracked as [Connect-time send-classification of integration actions](https://github.com/Dito-Core/dito/issues/8). The taxonomy above stands regardless of its outcome.

**Amendment 2026-08-29 (the gate lives on the tool).** Every unit of agentic work is now an execution created by a trigger ([ADR-0014](0014-runtime-harness-tool-runner.md)), and executions hold tools — including executions with no human present, steered by customer text. **The tool list rides in the execution's instructions**, deliberately, in its simplest form: the safety guarantee does not live there. It lives on the tools themselves — **every tool whose effect is externally visible carries a human-in-the-loop gate by construction**, so it is safe to expose in any execution. `create_draft` is the worked example: it produces an inert proposal that cannot reach a customer without a tap, so it does not matter who called it. Class 1 therefore remains unreachable from any tool surface, exactly as above.

Stated plainly because it was previously implicit: there are **two gate shapes, not one**. *Approve-before* for external or irreversible effects (the tap). *Disclosed-and-undoable-after* for Ledger writes — the provisional window of ADR-0004, which is the "automation that can be undone should skip the human" half of [ADR-0036](0036-no-architecture-tax-on-reps-or-owners.md). A tool must have one or the other.

**Named remainder — the rep notepad has neither.** [ADR-0033](0033-rep-notepad-is-twin-side-only.md)'s notepad is not external, is never disclosed, has no owner view by design, and is appended to the drafting prompt — so a write from an execution with no human in the room would shape every future draft and be invisible forever. A `write_notepad` tool owes a gate, decided when the tool is built. Also moved: the class-3 clause above exposes tools "only in live-rep-command contexts or automations in `active` state" — that moment now arrives at the *Automation primitives* chunk rather than at *Integrations beyond WhatsApp*, so [#8](https://github.com/Dito-Core/dito/issues/8) settles earlier than its placement on [#6](https://github.com/Dito-Core/dito/issues/6) assumed.

**Amendment 2026-09-02 (a read owes a projection, not a gate).** The two-shape rule above binds tools *with* externally visible effects; it said nothing about a tool with none, and slice 4's owner twin ([#112](https://github.com/Dito-Core/dito/issues/112), spec [#126](https://github.com/Dito-Core/dito/issues/126)) is the first execution whose tools are all reads. Stated now: **a read-only tool has no effect to gate and owes a projection** — by construction, three things. It runs as the surface's own database role, so what it *can* return is fixed by grant and row-level security, not by its code. Its parameters select rows — an entity, a window, a fact type, a seat — and never columns, tables or company. And the surface renders provenance from the rows the tool returned, refusing any citation to a row it never served. The checks are FR-71a's grant diff and a structural test, not a person.

Why not a third gate shape: the only candidate, *disclosed-after* (every read logged and shown to someone), has no legitimate recipient — the reps whose facts were read may not receive an owner-usage signal ([ADR-0025](0025-telemetry-content-free-wall-respecting.md)). And why not "nothing": a wall leak through a read is a projection leak, not an effect — a read whose reach the model controls (a column list, a table name, a query) is how the wall would fail without any effect at all. A tool declaration therefore carries one of three values — `approve-before`, `disclosed-and-undoable-after`, `projection` — and cannot be constructed without one. The glossary gains *Gate* and *Projection*; *scope* was not available, being the rep's chat set.

**Amendment 2026-09-03 (the moment is the first tool Dito did not write, not the runtime).** The 2026-08-29 amendment above moved [#8](https://github.com/Dito-Core/dito/issues/8) earlier on the strength of the class-3 exposure clause. That clause governs *when* a class-3 tool may appear, and the same amendment replaced context restriction with the gate on the tool as the safety — so it no longer fixes a moment, and it never asked #8's question, which is *which* of the tools Dito did not write are class 1 and which class 3. Every tool the runtime exposes through slice 5 ([#113](https://github.com/Dito-Core/dito/issues/113)) is Dito-authored, its class known when it is written, its gate declared at construction; class 3 has no member. What the sort has to be decided against — a provider, a tool manifest, whether MCP tool annotations are a usable signal — does not exist before the first integration. #8 therefore returns to the head of *Integrations beyond WhatsApp*, where the slicing first placed it, and no longer blocks slice 5.

It goes back carrying a second clause this ADR owes and had not named. Class 3's protection above — the intent record before execution, at-most-once across lease flips, unresolved outcomes held — is neither *approve-before* nor *disclosed-and-undoable-after*, so under "a tool must have one or the other" a class-3 tool cannot be declared as written. Whether class 3 is a third gate shape or collapses into approve-before is decided with #8, at the first integration, against a tool that exists.

**Amendment 2026-09-04 (the third shape: rep-evidenced).** The named remainder above — the rep notepad has neither gate — is decided at slice 5a ([#113](https://github.com/Dito-Core/dito/issues/113), spec [#171](https://github.com/Dito-Core/dito/issues/171)), and the answer covers more than the notepad. A tool that writes **twin-side state on a rep's behalf** — `write_notepad`, `dismiss_draft`, `decline_binding` — takes the id of a rep-authored twin-thread message as a required parameter and verifies, by code against the execution's trigger, that this message is the one that created the execution. A customer-triggered execution has no such message and structurally cannot call the tool, whatever its model was talked into; the danger the remainder named — a drafting execution with no human present writing a customer's sentence into the block that shapes every future draft — is closed on the tool, not on the tool list. This is [ADR-0003](0003-single-aperture-writer.md)'s class-2 rule — a rep act must reference verifiable rep-act evidence, matched by deterministic code — lifted onto twin-side state, where there is no correction window to be the gate. The shapes for effects are therefore three: *approve-before*, *disclosed-and-undoable-after*, *rep-evidenced*; a read still owes a projection. The Ledger rep acts (`retract_disclosure_line`, `answer_aperture_question`, the binding confirmation's filing) keep *disclosed-and-undoable-after* as their gate, because the window is what makes them reversible, and carry the same evidence under ADR-0003 as they always have.

Why not *approve-before*: it would put a keyword on an act the rep can edit or delete on the dashboard, which [ADR-0037](0037-the-twin-talks-like-a-coworker.md) reserves for acts that cannot be taken back. Why not *disclosed-and-undoable-after* alone: it fits the mechanics — the thread acknowledges the write, the dashboard undoes it — and misses where the danger is, which is who may trigger the write. Why not confining the tool to the twin-thread execution: the 2026-08-29 amendment above moved the safety off the tool list on purpose, and a rep assembling their own execution could pick the tool. The deferred twin-proposed half of the notepad ([ADR-0033](0033-rep-notepad-is-twin-side-only.md)) passes through the same door: the twin *proposes* in the thread — inert, like a draft — the rep answers in prose, and the answer's message id is the evidence.

Stated for the record at the slice-5a boundary ([#177](https://github.com/Dito-Core/dito/issues/177)): the *rep-evidenced* gate has two halves on two sides of the dependency wall. The runtime package checks the **shape** — a declaration under this gate names the parameter that carries the rep's message id, and one that does not, or does not require it, cannot be constructed. The owning app checks the **id** — against the trigger it holds, then against the seam row through the aperture's own verification — because the trigger and the seam are the app's and the runtime may not read either. Nothing in the package enforces the second half; an execution assembled with this tool and no trigger behind it is a type error today and a runtime refusal the day definitions are assembled dynamically, and that refusal is the app's to make.

**Amendment 2026-09-09 (the second surface).** The rep-evidenced gate's evidence widens from *the id of a rep-authored twin-thread message* to **a rep act on either surface**: a `dashboard_acts` row — the act, its target and the session that pressed it — is verified by code against the trigger and the seam exactly as a message id is, and a customer-triggered execution still has neither ([#224](https://github.com/Dito-Core/dito/issues/224); boundary ([#225](https://github.com/Dito-Core/dito/issues/225))). Two things the build made precise. A **scope switch** is an execution with a `dashboard` trigger, zero iterations, zero tokens and no tool list, and it does **not** pass through the gate: the gate is a fence on a tool a model chose, and here no model chose anything — the act row *is* the evidence and the execution is the record ([#223](https://github.com/Dito-Core/dito/issues/223)). And the gate stands **in front of an act and not only a page**: a POST is a request of its own, and every dashboard write checks the same durable facts the page read before it writes. The three shapes stand; a read still owes a projection.

**Amendment 2026-09-20 (the third evidence, and the closed set of three).** The 6b grilling ([#215](https://github.com/Dito-Core/dito/issues/215); spec [#258](https://github.com/Dito-Core/dito/issues/258) decisions 2 and 7) adds the third kind of evidence the rep-evidenced gate accepts: a **dashboard message** — the rep's words typed through *Habla con Dito*, sealed by the runtime and written under a login session — verified by code against the execution's trigger exactly as a self-chat message id is. The trigger it rides is the thread's own: occasion `twin_thread_message`, mechanism `seam_event`, the wake predicate widened to a second source, `dashboard`; the set of three mechanisms — seam event, request, schedule — stands, and **the dashboard is an occasion, never a mechanism**. Class 4 is unchanged by the twin speaking on the lock screen: a **knock** is a part of a post the execution wrote, never a send the model made, and notify reads it from the row ([ADR-0022](0022-system-outbound-rails-closed-notify-catalog.md)).

**Amendment 2026-09-27 (the thread's new tools, and the harness's own).** The harness change ([ADR-0014](0014-runtime-harness-tool-runner.md) as amended) adds tools, and every one carries a gate at construction as this ADR requires. **`spotlight`**: *disclosed-and-undoable-after* — the canvas shows the curation, and the next turn or the canvas's own fallback replaces it. **`knock`**: class 4 through notify, as before — a part on a post the thread may address, delivered by notify from the sealed row, never a send the model made; the floors are code. **`create_automation`**: *rep-evidenced* to create, in FR-75's pending state, and **a rep act on Rutinas to activate**, so an event-woken turn with no rep line behind it can author nothing. `start_workflow`, `steer_run`, `pause_run`, `cancel_run`: *disclosed-and-undoable-after* — visible in Trabajos en curso, cancel a flag. `ask_rep`: *approve-before* by shape, the answer being the act. `search_messages`, `read_message`, `read_post`, `read_entity`, `read_canvas`, `read_runs`, `read_automations`: *projection*. **The harness's own tools are mapped, not exempted.** Read, Glob and Grep on the twin's workspace directory are *projection* — the files are the twin's own, inside the unit. Write and Edit are *disclosed-and-undoable-after* through the runtime's snapshot at the step boundary ([ADR-0011](0011-workspace-artifacts-immutable-versions.md) as amended). WebSearch is *projection* under ZDR. Task inherits the parent's list and hooks. **Bash and WebFetch are off** — they would reach the network from inside the unit — until the unit's egress is enforced at the network, and then Bash only inside a workflow's `code` step (ruled 2026-09-27). A `PreToolUse` hook refuses any tool not on the definition's list, so the gate on the tool and the list in the instructions are both enforced by code, in that order; the harness's own permission model is off because these are the gates.

**Amendment 2026-10-02 (the hint column; what the guard and `create_draft` read).** The drafting lookup `resolve_chat` is a *projection* in the 2026-09-02 sense, and its pinned columns are now three: reference, name and **hint** — hint present only when two or more candidates' names fold to one label, made of the number's last four digits (none for a LID-addressed chat, which has no number to show) and the day the other side last wrote, in the seat's zone. The one conversation read it costs is an instant, never content, and a structural sweep keeps every row to exactly those three columns, with no address, no entity id and no content ([#300](https://github.com/Dito-Core/dito/issues/300), PR #301; the 6b boundary's F8, [#270](https://github.com/Dito-Core/dito/issues/270); [ADR-0039](0039-the-twin-asks-only-what-the-rep-can-settle.md) as amended). Two things follow on the tools. The guard holds an ask's prose — and the line beside a draft — to the served hints: the words after a hinted slot carry a key of their own chat and none of a sibling's, keyed on every part of the hint rather than on its text, so a paraphrase passes and a mispaired hint is refused before the rep sees a choice whose words point one way and whose references the other. And `create_draft` reads the rep's message for hint keys and refuses a draft to the chat the rep's own words point away from, before the act slot is claimed — a lookup over the rep's words, the way the binding-question rule reads them, never a keyword. Neither is a new gate: the hint is a column of a projection, and both checks ride on tools whose gates stand as declared.

**Amendment 2026-10-02 (the tools' references are stable ids — decided 2026-09-28, applied in the harness slice).** Wherever a tool names a customer it takes the entity's own stable id, and wherever the twin speaks of one it writes that id for code to render as the confirmed name (the agent architecture, D15, ruled by Diego on 2026-09-28; [#315](https://github.com/Dito-Core/dito/issues/315)). `resolve_chat` stays as a lookup by name that returns ids, callable whenever the twin wants; the per-execution served counter, the numbered slots, the guard's word matching against hint keys and the focus's re-serving of candidates all go — the amendment above describes them as built until then — and the one check left is that an id resolves to a row; one that does not sends the submission back. Still a projection: an id names a row the twin may see, code adds the number's tail to the rendered name only where the customer has more than one chat, and an address never reaches the model.

**Amendment 2026-10-02 (two rules from the dots recon).** Recorded from the OpenAI dots teardown ([#310](https://github.com/Dito-Core/dito/issues/310), R1 and R4), neither adding a check (Diego, 2026-09-29: agentic first). **An approval is keyed to one effect's stable id** — the tap to one draft, the act on a card to one post — and continuation, delegation and later runs never inherit it; there is no standing permission, which is what the code already keeps ([#294](https://github.com/Dito-Core/dito/issues/294), checked 2026-09-27; [ADR-0006](0006-send-lock-topology.md) as amended). And **gate code, the tap and the audit writer stay outside anything the model can write** — now, when the model's reach is the workspace directory on the twin's volume, and when Bash or egress opens under the 2026-09-27 amendment above: a gate a model could edit is no gate.

**Amendment 2026-10-06 (built: the run tools; the gate is on the tool inside a run too).** The run tools are built with exactly the gates declared ([#323](https://github.com/Dito-Core/dito/issues/323)): `start_workflow`, `steer_run`, `pause_run` and `cancel_run` disclosed-and-undoable-after — a run is visible in Trabajos en curso the moment its row exists and cancel is the undo — and `read_runs` a projection over pinned columns; `pause_run` takes `paused: true | false`, so Reanudar exists beside Pausar and Cancelar, all three as dashboard acts on a run target. None needs rep evidence, so an event-woken turn may start work the rep asked for earlier. Three thread tools landed with their gates since the last line: `write_working_memory` disclosed-and-undoable-after ([#322](https://github.com/Dito-Core/dito/issues/322)), `fill_blank` approve-before — it writes into a draft the tap still covers ([#342](https://github.com/Dito-Core/dito/issues/342)), `say_on_card` disclosed-and-undoable-after ([#340](https://github.com/Dito-Core/dito/issues/340)). `knock` is declared disclosed-and-undoable-after, the nearest of the three words (class 4 is held by the dependency wall; notify is never a tool). The harness's own file tools are **not served today** (`tools: []`); their mapping above stays decided for when they are. The stable-reference change of 2026-10-02 is built ([#321](https://github.com/Dito-Core/dito/issues/321)). **Reversed 2026-10-06 (Diego).** The 2026-09-27 line that a run's `act` step is the one place an effect happens and that an `agent` step holds the thread's reads only is withdrawn: inside a run as in the thread, **the `agent` step holds every registered tool under that tool's own gate** and calls it itself; the gate sits on the tool, never on a list — a `run_step` trigger carries no rep line, so a rep-evidenced tool refuses inside a run by its gate, not by exclusion; `act` stays as an optional no-model call with mapped inputs and `check` goes ([#324](https://github.com/Dito-Core/dito/issues/324)). **`ask` is one tool with two callers**: the thread asks and continues; an `agent` step that asks ends with the disposition `asked` and the engine parks the run on the card — the tool posts, the engine parks, the model only asks. `create_automation` rep-evidenced to create and Activar as the rep's act stand ([#325](https://github.com/Dito-Core/dito/issues/325)).

**Amendment 2026-10-07 (decided: no submission tool; the words and the typed result are the SDK's).** The gate is on the tool, and a submission tool was never an effect — it was the model filling a form to be allowed to finish. Ruled 2026-10-07: it goes ([#357](https://github.com/Dito-Core/dito/issues/357) for the run step, [#363](https://github.com/Dito-Core/dito/issues/363) for the four conversations). The twin's words are the model's final message; a typed result is the SDK's structured output; every effect is a registered tool under its own gate, exactly as this ADR has always said. The thread's `submit_answer` side-channels dissolve into what they already are: the customers it names are `[c7]` references code renders, the candidates of an ask are those references offered with their hints, the chat it confirms is the unconfirmed chat it references, the knock is the `knock` tool; the guard sweeps the final message. Decision 19 stands: `answer_ask` is rep-evidenced, and the thread does not post a typed question card outside a run (ruled 2026-10-07).

**Amendment 2026-10-08 (built: the binding tool, the SDK's tools under gates, the submission arm gone).** The 2026-10-07 amendment said the chat the thread confirms «is the unconfirmed chat it references» — a reading of the words. That was wrong by this ADR's own rule and by the glossary's *Hand-off*: a binding question is a card code renders from an effect. Built in [#363](https://github.com/Dito-Core/dito/issues/363) (PR #367): the thread asks through **`propose_binding`**, approve-before, beside `decline_binding`; the sentence fence it shares with `create_draft`'s binding question is one module; nothing reads intent off the twin's words, and the owner twin's dispositions are read from the turn — `wall-refused` only when a read tool refused, `asked` for an open choice, `schema-miss` the runtime's word for a typed result it could not accept, the model's «no such fact type» an answer kind of its own (`unrecorded`). [#326](https://github.com/Dito-Core/dito/issues/326) (PR #369) names the SDK's `Read`, `Glob`, `Grep`, `Write`, `Edit` and `WebSearch` on a definition like any tool, each under a gate of its own (`SDK_TOOL_GATES`: the reads are projections over the workspace directory, a write is disclosed-and-undoable-after through its version), confined to the workspace by a `PreToolUse` hook and recorded as the performed effect `wrote` by a `PostToolUse` hook; Bash and WebFetch are refused by name. [#364](https://github.com/Dito-Core/dito/issues/364) (PR #370) gave extraction and the disclosure their effects as gated tools held by Dito's definitions alone — `file_facts` (disclosed-and-undoable-after under the correction window) and `post_disclosure` — and deleted the submission arm of the execution package with the older definition kind.

**Amendment 2026-10-11 (a rutina's gate follows who asked, on the twin's word).** The 2026-09-27 sentence «`create_automation`: rep-evidenced to create, in FR-75's pending state, and a rep act on Rutinas to activate» and its 2026-10-06 restatement are superseded (boundary [#327](https://github.com/Dito-Core/dito/issues/327); Diego's ruling of 2026-10-11 after the Grok Bot routines research, which found every peer confirming a scheduled job once, where it was asked, and found a rep who asks on the phone with no way to activate on Rutinas). **`create_automation` is *disclosed-and-undoable-after* when the rep asked**: the row is active at birth, Rutinas shows it at once, the switch and Descartar are the undo, and the first firing waits for the next instant at or after the ask. **When the twin proposed, the gate is *approve-before* on the proposal card**: a post with a `proposal` part at both doors, Activar or the rep's yes in prose makes it active, Descartar ends it, nothing fires before. **Which of the two it was is the twin's word (`asked_by`), and no code checks it** against the turn, the message or anything else — Diego, 2026-10-11, verbatim: «DO NOT PUT ANY ENFORCEMENT OF CODE AND TRUST THE MODEL»; the `evidence` parameter and its check are gone from the tool. The rep's prose answer to a proposal is the thread's `answer_proposal`, *rep-evidenced* in `answer_ask`'s shape, calling the same store functions the card's buttons call. **Only the thread creates automations**: `create_automation` is excluded from every run step's tool list by the list, not by a check — a run that wrote a rutina would write it again at every firing ([#386](https://github.com/Dito-Core/dito/issues/386), PR #388).
