# The entity model, and how two entities become one

**One entity type.** An entity is the Ledger's anchor for a customer, carrying a `kind` label (person | business) that exists for display and for merge safety and **changes no behaviour anywhere else** — the moment `kind` branches the fact model, the grant model, or retrieval, we have rebuilt the CRM Contact/Account split the glossary deliberately rejected. The person↔business relationship is not modelled: facts attach to the customer, and which human at that customer said them is not a Ledger concern — ADR-0004 already bars chat identity from owner-visible provenance, so modelling contacts would build a structure the wall forbids populating. Many chats may bind to one entity, which is how a business with several people messaging one rep stays one customer.

**Rep-side mints identity.** The entity id is a client-minted UUID, created on the rep's device when the rep confirms a binding, and it becomes the Ledger entity id unchanged — there is no reconciliation step and the bundle's entity mirror stays a mirror rather than a translation table. This is not a wall violation: the aperture is itself rep-side (ADR-0003), and the binding ceremony already produces a well-formed class-2 rep act, evidence-bound to the WA message id of the rep's own confirmation. The real benefit is idempotency — a client-minted id makes "this chat is Fuentes" safe to retry over a flaky mobile network, which is why AIP-133 and Stripe's idempotency keys take the same shape. Two consequences follow: the aperture must scope every id by company **server-side** and never accept a company scope from the device (client-supplied ids are client-supplied data); and because random UUIDs carry no ordering, the entity row stores `created_at` and survivorship is decided by a written rule rather than by whichever row a query returns first.

**Every fact attaches to exactly one entity, and there is no non-entity slot.** FR-32's orphan rule is absolute. A market- or season-level observation — *"December is slow for construction"* — has no entity, and therefore no timeline, no grant, and no index: it is unreachable by the entire access model, because entity-scoping is what makes access control and relevance the same mechanism. It is also the wrong side of the aperture test, sitting close to the *"rep tactics, judgments, or selling approach"* FR-30 excludes by name, and a slot for entity-less observations is the natural drain for exactly the rep-level inference ADR-0033 exists to prevent. A candidate with no entity becomes a question and expires (FR-32), which is already the shipped behaviour. Revisit condition: the failed-query log at the pilot review. If it ever earns a place, it returns as a **company entity** reusing this machinery, never as a parallel scope.

**Merge is a redirect, and the merge edge is immutable.** The losing entity keeps its row and gains a pointer at the winner; facts never move; the loser's id stays resolvable forever. That shape is standard prior art — HL7 FHIR's `Patient.link` with `replaced-by`, Dataverse's non-expiring tombstone, Reltio's *"the losing entity ID is not deleted… can still be used in API calls."* The stored edge records the merge that actually happened (`A merged_into B`) and is **never rewritten**; the transitive resolution is a derived, rebuildable projection. Flattening `A→B→C` into `A→C` at merge time is the one thing not to do: MediaWiki shipped it, found it *"cannot function properly"*, and removed it in 1.39 — and in an append-only store it is worse than a performance bug, because it writes down a merge nobody performed. The edge carries a **status** (`merged`, a genuine same-customer, versus `created_in_error`, a duplicate that should never have existed — they mean opposite things for whether the loser's facts read forward), the **effect set** at merge time (unreconstructable afterwards, per FHIR and Reltio both), and a **human-or-machine stamp**, which is what makes any claim about automation provable in the data rather than asserted in a document. A cycle check is mandatory. **A merge never deduplicates facts**: two reps who each filed the same promised date filed two true assertions with separate provenance, and collapsing them would destroy provenance and invent a fact nobody filed.

**Merge is automatic, deterministic, and asks nobody** — see ADR-0036 for the principle. Within one company, two entities merge when they share a **tax ID (RFC)**, or a **normalized email**, or a **normalized phone with matching `kind`** — phone carries the extra condition because a shared switchboard number is not entity-unique. **A matching name is never sufficient**: names collide, and two *Ferretería Fuentes* in different cities is the case that would fuse two real customers with nobody watching. Below the ladder nothing happens and both records persist, which is also Salesforce's shipped default for this exact scenario. Deterministic keys were chosen over a scored threshold because with zero entities in existence any threshold would be invented rather than derived; the ladder needs no tuning and is explainable in one sentence. This makes identifier normalization a **payload obligation** — `ContactEstablished` carries structured, multi-valued, normalized identifiers (E.164 phone, lowercased email, uppercased RFC), not free text, because under ADR-0034 fields can be added later but what is already stored cannot be restructured. The matcher runs Ledger-side on Ledger data only and never reads a binding or a chat JID (ADR-0004). Expansion — a retriever plus batched LLM adjudication for the fuzzy cases — waits on the instrumentation, not on appetite.

**What justifies dropping the human is reversibility, not confirmation.** The instinct that a person confirming makes a merge safer is measurably false: the ONS measured an automatic false-positive rate of 0.005% against 0.648% for human clerical review — roughly 130× worse, and that was *with* best-of-three redundancy nobody here would have. Safety comes from the merge being non-destructive and undoable by construction, which is what the immutable edge, the recorded effect set, and facts-never-move buy. Note honestly that **"never auto-merge" has no prior art** — AHIMA, IBM, Oracle and IHS all ship an auto-link band, and the PRD's position was the unusual one; what the evidence does support is that erring toward review is the safe *direction*, because a wrong merge is far more expensive to unpick than a missed duplicate.

**Grants attach to the entity a fact was filed against, not the resolved one.** This is what stops a merge from becoming privilege escalation: a rep's creation grant returns the facts that rep filed, and merging never hands them another rep's. Cross-rep reading stays owner-assigned and deliberate.

Chosen so the Ledger can hold one customer's history honestly without anyone being conscripted into maintaining it, and so that every mistake it makes is one we can find and reverse.

**Amendment 2026-08-30 (the unmerge; Dito-Core/dito#62).** What slice 3 shipped was *undoable data, not an undo* — the immutable edge, the effect set and facts-never-move were all in place, and there was no verb, so ADR-0036's rule was spending a mechanism that did not exist. It exists now, and four things follow that a reader of the paragraphs above would otherwise get wrong.

**An unmerge is an appended reversal, and the edge stays immutable.** A second table records that one edge no longer stands; the edge itself is untouched, because *"surfaced / merged / reversed per company per week"* is the instrumentation this design gates its own expansion on, and it is unanswerable from a graph that forgets its mistakes. **Resolution and every other walk therefore follow the edges that still stand** — the derived projection is over active edges, not over all of them. Nothing else changes: no fact moves, is deleted or is reassigned, before the merge or after it, and no grant is written or revoked. That is what makes the undo cheap here and impossible in the MDM products the research surveyed, where the contributor stopped being an independently-keyed record. Reversing a `created_in_error` edge is the statement that the record should have existed after all: its facts are its own again, and its identifiers are match keys again.

**"One out-edge per loser" now means one that still stands.** Stated as a unique index it made an entity a loser once in its life, so an unmerge would have cost the record its future. The rule is unchanged; it is enforced in the store's trigger, under the same company lock as the mandatory cycle check, because no index can carry a predicate over a second table.

**A reversal binds the automation, not the human.** An unmerge moves no fact, so the identifier that fired the merge is still filed against both records and the ladder would find it again on the next daily pass — an undo that survives until the evening is not an undo. A reversal is therefore a standing statement that those two records are not one customer: the matcher skips the pair and says so. A human may still merge them deliberately, which files a new edge and never resurrects the reversed one.

**The operator invokes it, audit-chained**, in ADR-0016's break-glass shape — not the rep (ADR-0036: the rep who could judge a cross-rep duplicate is structurally prevented from seeing it), not the owner (no entity surface, and the same rule), and not the machine (nothing detects a wrong merge; the `reversed` count begins with this verb). The hand trigger stamps `human` and offers no flag, because a hand trigger *is* a human and the stamp exists so that a claim about automation is provable in the data; the store carries `machine` for the day a detector arrives, exactly as it carried `human` before any human merge verb existed. The chain records the refused and repeated attempts too, with their own outcomes: a break-glass verb is where "somebody tried and was told no" is the question. The trigger's listing prints opaque ids by default and the two records' names only when asked, because an audited session's stdout is a retained surface and ADR-0020's rule for those is opaque ids. **An unmerge is not disclosed**, for the reason a merge is not (ADR-0003 as amended): it files no fact, moves nothing across the wall, and rearranges company data that already crossed and already had its window.

**Amendment 2026-08-31 (`kind` is determined, not defaulted; Dito-Core/dito#60).** *"A normalized phone with matching `kind`"* was written as a condition that could be evaluated, and for the whole of slice 3 it could not: the binding ceremony had no verb that told a person from a business, so every entity was filed `person` and the rung's extra condition compared two placeholders. **The model determines it now**, at binding confirmation, from the name the rep confirmed and that chat's own words — and it always records its best determination. There is no third value and no NULL, because a NULL `kind` can never phone-match, which would leave the rung inert for exactly the records that need it: an entity claiming nothing and an entity claiming `person` produce the same non-answer. The judgement is easy — «Ferretería Fuentes» against «Ana García» is the shape of the whole problem — and the error is the recoverable kind: a wrong `kind` either blocks a merge that should have happened, where nothing crosses and the records can still be joined deliberately, or allows one that should not, which is what the unmerge above exists for. Neither writes a false fact. The rep is not asked, per [ADR-0036](0036-no-architecture-tax-on-reps-or-owners.md): the ceremony's «va» settles which customer a chat is, and a second question would be work that exists only because of how Dito is built.

**The determination is class-1 output, and its fence is a privilege.** The entity is created by a class-2 rep act (ADR-0003) and the aperture's grant on the entity table is a COLUMN-level `UPDATE (kind)` and nothing else — so an inference can set the label and can never create a customer or rename one. What that buys today is the grant audit, red the moment either half stops being true, because nothing yet authenticates as `dito_aperture`; the day something does, the fence is the database's rather than the audit's, and nothing else changes. **A model never overrules a person**: once a human has determined a kind, only another human changes it, refused inside the writer's own unit rather than remembered by a caller. Every determination is audit-chained under its own action word with a `model`-or-`human` stamp, so *"which of these did anybody actually look at"* is answerable from the chain; the sequence of entries is also what the previous value was. **A kind change is not disclosed**, for the reason a merge is not (ADR-0003 as amended): it carries no name across and files no fact. That it changes merge eligibility is the argument the other way, and it fails on its own terms — the merge itself is not disclosed, so a change to what a merge is eligible for cannot owe the rep more of a disclosure than the merge itself does.

**A `kind` change takes the same company lock a merge does**, because it decides what the ladder may do: the matcher reads the kinds, decides and writes inside one transaction, and a correction committing in between would leave it merging on a kind that stopped being true while it was deciding.

**Correcting one is the operator's, by hand, like the unmerge** — there is no rep or owner surface for entities, and nothing detects that a determination was wrong. A wrong one is SEEN two ways: the operator's listing puts each kind beside the name the rep confirmed, and the ladder's `kind_mismatch` skips are now printed by the extraction trigger, so a label keeping two records apart says so in a number. **Correcting a `kind` never re-merges anything.** A pair a human took apart stays apart forever (the amendment above), so a fix that makes a merge correct after an unmerge still needs a deliberate `fileMerge`; a fix that unblocks a merge nobody ever made needs the ladder climbed again, which the daily pass does only on a day it read a chat — so on a quiet company that is the hand trigger's job, exactly as this design's reconciliation already was.
